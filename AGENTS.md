# AGENTS.md: Jev Dungeon

Guide for AI coding agents (and humans) about to change this game. Full API signatures live in [CONTRACT.md](CONTRACT.md); this file tells you how not to break things. **Touching any art, colour or animation in `public/`? Read [STYLE_GUIDELINES.md](STYLE_GUIDELINES.md) first** (palette ramps, sizes, construction techniques, the reference sprites). CONTRACT.md was brought in line with the code after the memory redesign and the skills work (explorer and adversary memory, settings, skills).

## Architecture

One game is a `Run` (src/turn.js). The explorer sees the world only through a `KnownWorld`; each adversary reads the `Game` through its own `AdversaryView` (the real map by default; a limited known set with the `limitedMap` toggle). Jev calls are injected, so every check runs without the network.

| Class | File | Role |
| --- | --- | --- |
| `Game` | `src/dungeon.js` | One game's state (position, lighting, lives, grace, adversaries) and its rules: `applyMove`, `damage`, `isKnown`, `knownTile`, `legalMoves`, `availableMoves`, `knownFloorCount`, `exploredPct`, `publicView`, `twin`. Public fields on purpose: the checks set them. |
| `KnownWorld` | `src/characters/explorer/known-world.js` | The explorer's only window on a `Game` (private `#game`): own state, lit cells, adversaries in sight, the portal (`seenTreasure()`) once lit, and `move(dir)`. All explorer perception, brain and memory code takes a `world`, never a `game`. |
| `ExplorerBrain` | `src/characters/explorer/brain.js` | One explorer: plain-JSON `memory` plus private bookkeeping, `takeTurn()`, `noteHit()`, `noteCaught()`. Built as `new ExplorerBrain(world, { ask, memoryDir })`. |
| `Adversary` | `src/characters/adversary/adversary.js` | One ghost. Six public fields (`id, pos, mode, budget, lastSeen, goal`); hunt state, patrol route, last request body and its fixed `character` (a preset id, default `'standard'`) are private, behind accessors. |
| `AdversaryView` | `src/characters/adversary/adversary-view.js` | One ghost's window on a `Game` (private `#game`), the ghost-side twin of `KnownWorld`. Mode `full` reads the real map (today's behaviour); mode `limited` (the `limitedMap` toggle) knows only a set K of cells. All adversary perception, brain and memory code takes a `view`, never a `game`. |
| `Run` | `src/turn.js` | One game in progress: `run.game`, `run.explorer`, `run.memory`, `await run.playTurn()`, `run.view()`, `await run.persist()` (writes the opening memory files; `server.js` calls it for every new game, the checks do not). Made by `newGame(seed, opts)` / `newTestGame(config, opts)`. |

Explorer modules form a chain: `known-map.js` (pure known-floor helpers) ← `encounter.js` (encounter model) ← `perception.js` (approaches, tactic options, situation, move facts) ← `brain.js`. No file in the chain imports a later one, so keep it acyclic.

`opts = { ask, decide, dir, memoryDir, confidence, hold }` (all optional; `confidence` is an optional arm object `{ start, wPerExtra, weights, model, fixedMood }` for checks and measurements: the explorer's confidence caps its moods always (PLAN-moods), so there is no toggle; `fixedMood: true` pins the four classic moods so the duel harness and the request-size checks can measure the hold and the sizes without C moving the mood; `hold` (default `'multi'`) the engage hold: `true` holds against one enemy only, `false` is no hold (duel checks only), `'multi'` also holds against 2-3 enemies in sight). `ask` replaces the explorer's Jev call, `decide` the adversaries', `memoryDir` is where `memory.json`/`memory.md` go, `dir` where `adversaries.json` goes. Omitting `ask` or `decide` means the real, paid Jev.

## Read this first

1. **Fog of war is a hard rule.** Jev may only receive *known* (lit) cells, adversaries the explorer can *see right now*, and (user-approved amendments) adversaries it **saw earlier, frozen at the moment of sighting** (`threats.remembered`), and the **health bar (`hp`), `level` and `clawDamage` of an adversary in sight** (all three are in-sight reads from `KnownWorld.visibleAdversaries()`, frozen with the sighting once it is out of sight; levels are PLAN-levels); an unseen adversary's hp, level or claw never reaches Jev. The brain records a sighting only from `visibleAdversaries()`, never moves it, and drops it after `REMEMBER_STEPS = 30` steps or as soon as the explorer stands within `SIGHT_RANGE` of the frozen cell with a known line of sight to it while that id is not visible (the cell is seen empty). A remembered sighting never reveals where an adversary is now. Explorer code (`src/characters/explorer/*` except `known-world.js`) reads the game only through `KnownWorld`: never hold a `Game`, never touch `dungeon.tiles`, `dungeon.rooms`, `dungeon.treasure`, `floorCount`, `isFloor` or `floorDistances`. A **static guard** (section 0 of `check-dungeon.mjs`) fails on `game.x`, `game[...]`, `.dungeon`, dynamic or namespace imports, and any import outside its allowlist (`DIRS`, `LIGHT_RADIUS`, `STAY`, `EXPLORER_LIVES`, `SIGHT_RANGE` from dungeon.js; `ADVERSARY_SPEED`, `GRACE_TICKS` from adversary.js; `buildSkillSet`, `skillConfig` from skills/loadouts.js; `skillQuestion`, `pickSkill` from skills/question.js; sibling explorer files, which now includes `./confidence.js`, listed explicitly in the check's allowlist (PLAN-confidence C2): a pure module that imports nothing, `check-confidence.mjs` asserts it; `./progress.js` is listed the same way (pure, imports nothing, `check-progress.mjs` asserts it); jev.js). If you need a new read, add it to `KnownWorld` and make sure it is fog-safe. The checks also run "twin" tests that scramble hidden state and require byte-identical Jev input; the remembered-sighting twins move a hidden adversary after the sighting and require the same request.
2. **Jev calls cost money. In the game only `POST /api/step` makes them.** Each step makes one explorer call (two on a decision tick: sentiment, then tactic + move), unless the move is forced, plus one call per hunting adversary. Every call is hedged (a second copy only after `HEDGE_DELAY_MS` = 800 ms without an answer) and retried (429, 502, 503, 504, 529). The other paid paths are `node scripts/run-testbed.mjs --live` and `node scripts/measure-memory.mjs --live`. Page load, `GET /api/state`, `POST /api/new`, every `scripts/check-*.mjs`, `run-testbed.mjs` and `measure-memory.mjs` without `--live` are free. Don't press Start, hit `/api/step` or pass `--live` to "test" something unless the user asked for a live run. In code, a `Run`, `ExplorerBrain` or `stepAdversaries` call **without an injected `ask` / `decide` is a paid path**: always pass stubs in scripts (the `check-*.mjs` scripts and the dry runs of `measure-memory.mjs` also replace `globalThis.fetch` with a throwing tripwire, so a miss fails instead of billing).
3. **Code beats the docs.** CONTRACT.md matches the code today. If you find a difference, the code is right: fix the doc, don't "fix" code back to a number written there.
4. **Never JSON-clone or spread a `Game`.** `game.litOutside` is a `Set`, and the methods live on the prototype, so a clone breaks `isKnown` near the map edge. For a modified copy (twin tests) use `game.twin(overrides)`, a shallow copy that keeps the prototype and shares whatever you don't override. The same goes for an `Adversary`: its hunt state is private, so only `new Adversary({...})` makes a working one.
5. **New files in `public/` must be registered in `server.js` `STATIC`** (server.js:23-32). Anything not listed there returns 404.
6. **A touch is a bump, not damage. Only attacks take lives.** An adversary on the explorer's cell is knocked off it with a `bump` event and nobody loses a life. A life is lost only to a claw strike (`hit` event; see [Skills](#skills-attack-and-block) and [Damage](#damage-strikes-grace-bumps)). Grace (`GRACE_TICKS`) and the one-hit-per-tick latch apply to strikes. The game is lost only at 0 lives (`hit` then `caught`). Don't make a touch hurt again, and don't add an instant loss in a new code path.
7. **Don't hand-edit `memory.json`, `memory.md` or `adversaries.json` (every hub instance has its own copies under `runs/<kind>/<name>/`).** They are runtime output, rewritten every step. (`settings-<port>.json` is written by the `/settings` page, see [Server & UI](#server--ui).)
8. **Seeds are deterministic.** Adding, removing or reordering `rng()` calls in `generateDungeon` or `spawnAdversaries` changes every seed's dungeon. `SPAWN_STEPS` (dungeon.js:28) mirrors `MIN_SPAWN_STEPS` (adversary.js), so change them together.
9. **Only edit files your role owns** ([table below](#repo-map--ownership)), unless the user authorises more. Other sessions may be editing `public/` (or other files) at the same time, so re-read a file before you edit it, and don't commit unless asked. The repo is git (branch `main`): check `git status` before you start.
10. **Test explorer behaviour in the testbed, not in a full dungeon.** `src/testbed.js` builds a small configured arena (size, adversaries, props, chest, or an ASCII map). Use it for any test of how the explorer reacts, and **extend it when your test needs a new knob**: add the option to `DEFAULTS` + `normalizeConfig`, a check in `scripts/check-testbed.mjs`, and a row in [Testbed](#testbed-small-test-arenas). Don't hand-build one-off arenas elsewhere (the check scripts' hand-built `Game`s are the exception). To run several arenas or dungeons side by side with different settings, use the hub (`/arena/<name>/`, `/gym/<name>/`, `node scripts/arenas.mjs`; see Run & verify), not extra hand-started servers. `dungeon.treasure` **may be `null`** in a testbed arena, so guard any new code that reads it.

## Overview

Jev, a paid decision API at TypeSafe (`api.typesafe.ai/v1/systemone`), steers a knight through a procedurally generated grid dungeon one cell per tick, looking for loot and the portal out (stepping on it leaves the dungeon and ends the game; score = coins held). Every visited cell permanently lights everything within `LIGHT_RADIUS`, and lit cells are the explorer's known territory. Grey ghost adversaries patrol. When one sees the explorer it switches on its own Jev brain and hunts. An adjacent enemy can claw away lives (4 by default); the game is lost when the last life goes and won only when the explorer steps through the portal. Portal-less testbed arenas retain their clear-all-enemies win (see [Victory](#victory)). The browser shows an isometric 8-bit view. Most numbers below are defaults: the gameplay tunables live in `src/settings.js` and are edited on the `/settings` page (see [Server & UI](#server--ui)). The Node server holds a single game in memory and makes every Jev call. The API key never reaches the browser.

## Conventions

- **Cells** are `[x, y]`, with x from 0 to `width-1` and y from 0 to `height-1`. **y points down.** `tiles[y][x]` is `'#'` or `'.'`. Cell keys are `` `${x},${y}` ``.
- **`DIRS`** = `{ up: [0,-1], down: [0,1], left: [-1,0], right: [1,0] }` (dungeon.js:30).
- **Map size varies per level.** Always use `dungeon.width`/`dungeon.height`; there are no size constants.
- **One tick** is the explorer's step, then the adversaries' moves. The explorer moves first, and a win on its step ends the tick before the adversaries move.
- **Code style:**
  - ES modules with named exports, `node:` import prefixes, `.js` on relative imports, `.mjs` for scripts.
  - 2-space indent, single quotes, semicolons.
  - PascalCase classes with `#private` fields for state nobody else may touch (`Game` and `Adversary`'s six fields stay public on purpose). camelCase functions, UPPER_SNAKE constants, snake_case keys in shapes sent to Jev or the browser (`explored_pct`, `known_floor_cells`).
  - Each file opens with a `//` header comment on its purpose. Inline comments explain *why*.
  - British vs US spelling is mixed (`neighbour`, `colour`, `centre`/`center`). Match the surrounding file.

## World & perception

**`src/dungeon.js`** (no Jev knowledge)
- Constants (dungeon.js:9-15): `LIGHT_RADIUS = 7`, `SIGHT_RANGE = 7`, `MIN_SIZE = 25`, `MAX_SIZE = 90` (code defaults, which the checks use; `central-config.yaml` sets `world.size` to 40..120 for longer linear dungeons, knob range 25..150), `EXPLORER_LIVES = 4` are `export let` defaults that `src/settings.js` changes through `configureWorld()` (importers see the live value; `SIGHT_RANGE` applies at once, the rest from the next game). `ROOM_MIN = 4` and `ROOM_MAX = 15` are fixed. The room-count divisor (`ROOM_AREA`, 290) is a private tunable.
- Generation: two layouts, picked by the `layout` knob (`world.layout`, `linear` (default) | `maze`, file-only, `when: 'next'`; `LAYOUT` in dungeon.js, set by `configureWorld`). Width and height are drawn first from the seed in both, so a seed keeps its size across layouts. All generator code lives in dungeon.js (check-props copies that one file).
- **Linear layout** (the default): one long winding path of rooms from the start to the portal, with a few side rooms. "The only way out is through."
  - A coarse grid of patches covers the map (patch side scales with the smaller map side, so a 25x25 map still gets a 2x2 grid). Each patch is inset 1 cell from its grid cell, so two patches are always at least 2 wall cells apart; a room and its corridor stubs carve only inside their own patch, and a corridor between two neighbouring patches carves only inside the rectangle spanning those two patches and the strip between them. The room graph is therefore fixed by construction: distortion can never add a link.
  - The **main path** is a self-avoiding walk over the patch grid that tends to keep its heading, so it winds (about 5 rooms on a small map, up to about 16 on 90x90). The start is the centre of its first room, the portal sits inside its last room's box (made larger, 8-neighbour clear for the 2x2 portal sprite, far from the entrance).
  - **Side rooms**: 2-5 dead-end rooms off main-path rooms (never off the portal room), now and then two deep. A **loop** (about 1 map in 2) is a side room on the inside corner of a turn, linked to path rooms i and i+2: a short detour around one room, never a shortcut past more than one.
  - **Organic rooms**: each room starts as a rectangle, gains 1-2 overlapping lobes, has its edge band roughened and smoothed by a cellular-automaton pass, keeps a protected core (the start and the portal stay clear) and only its largest connected piece.
  - **Corridors** wander from room to room inside their rectangle with a pull toward the target, 3-6 cells wide (the width drifts along the way), always at least a cell narrower than the smaller room it joins (`CORRIDOR_MIN` / `CORRIDOR_MAX` in dungeon.js), so 2-3 characters fit abreast and rooms stay larger. Rooms are at least 5 cells a side where the patch allows. A side-step that would push the brush against the corridor's rectangle is skipped (a clipped brush pinches). Floor not reachable from the start is filled back to wall.
  - Distortion shrinks on retries, and the last attempt is undistorted (rectangles, straight 3-wide corridors), which is always valid, so the retry loop cannot hang.
  - `dungeon.rooms` entries are the room's tight bounding box `{ x, y, w, h }` plus `role` (`start` | `path` | `portal` | `side`) and `order` (index along the main path). `dungeon.layout` (`{ kind: 'linear', patches, links }`) is hidden state for spawning and checks only: explorer code never reads it (fog guard). The maze layout has no `role`, `order` or `layout`.
  - Checks: `scripts/check-layout.mjs` (determinism, wall ring, all floor reachable, blocking any path room's patch cuts the start off from the portal except the room a loop bypasses, side rooms are dead ends, portal clearance, corridor widths).
- **Maze layout** (the old generator, unchanged byte for byte):
  - Room count is `max(4, round(area/ROOM_AREA))` (default 290), placed by rejection with a wall gap between rooms.
  - L-shaped corridors join the rooms via a Prim MST, plus about n/4 loop corridors.
  - The outer ring is always wall. The start is a random room centre.
  - The treasure is a room cell at BFS distance ≥ 60% of the farthest reachable cell, preferring cells whose 8 neighbours are all floor (the portal is drawn 2x2; the pool is filtered, so `generateDungeon`'s `rand()` count is unchanged). `placeProps` reads the treasure cell, so this change (d12e164) moved props, and with them tiles, ghost spawns and coins, on most seeds (16 of 20); rooms, corridors, start and size are unchanged. Testbed arenas are not affected.
  - It retries on the same PRNG stream if constraints fail.
- `placeProps` treats a linear room's walls as the wall cells with that room's floor in front (an irregular room has few cells on its bounding box edge); for a rectangular maze room that is the same set as before.
- Lighting:
  - Every cell within Euclidean `LIGHT_RADIUS` of a visited cell gets brightness `round((1 - d/(R+1))*100)/100`. Line of sight is not needed.
  - Brightness only ever goes up. `light > 0` means known.
  - With the default R = 7 the range is **0.13 to 1.0**.
- Off-map cells that get lit go into `game.litOutside` and count as known wall. That keeps the map edge indistinguishable from rock, which is intentional.
- Line of sight: `hasLineOfSight` walks a supercover line between cell centres, with endpoints ordered so the result is symmetric. It uses the real tiles. Any `'#'` strictly between the endpoints blocks, and a line through a corner needs both side cells open. **Sight** = LOS and Euclidean distance ≤ `SIGHT_RANGE`.
- **`Game`** (`new Game(dungeon)`) lives in dungeon.js, not its own file, because `check-props.mjs` copies that one file to a temp dir: keep the line `import { placeProps } from './props/place.js';` byte-identical and add no other relative import there. Fields are public and set up in the constructor: `dungeon, pos, steps, visits, light, knownCount, knownFloor, litOutside, floorCount, won, lost, caughtBy, health, maxHealth, graceTicks, trail, adversaries, adversaryTicks, patrolRand, facing, block, strikes, skillRand, coinPiles, coins, coinRand` (facing, block, strikes and skillRand are the skills state: facing, shield stance, this tick's strikes, the block-roll RNG; the last three are coins, see [Coins](#coins)). `adversaryTicks` (world ticks the adversaries have run) and `patrolRand` (patrol RNG, created lazily on the first patrol goal) belong to adversary.js but live here so there is no per-game WeakMap. `dispelled` is the tick's dispels (`[{ id, at }]`, written by `resolveAttack`, emptied by `clearTickState`): the death cry of [monster morale](#monster-morale-plan-monster-morale) reads it.
- Methods: `applyMove(dir)` returns `{ moved, revealed, revisit, won }` (plus `stayed` for `STAY`) and is a no-op once won or lost. `damage(amount, sourceId)` takes lives off, is a no-op once won or lost, sets `lost` and `caughtBy` only when health reaches 0, and returns `{ health, lost }`. `legalMoves`, `availableMoves`, `isKnown`, `knownTile`, `knownFloorCount`, `exploredPct`, `skillRandom()`, `clearTickState()`, `publicView` (sends `health`, `max_health`, `facing` and `strikes`; the pane draws hearts), and `twin(overrides)` (see rule 4). `EXPLORER_LIVES` defaults to 4.
- `publicView` sends the full `tiles` to the browser, for the debug Reveal toggle only. The renderer must still hide them; see [Server & UI](#server--ui).

**`src/characters/explorer/known-world.js`** (`KnownWorld`): wraps a `Game` in `#game` and exposes only fog-safe, live (never cached) reads: `pos`, `steps`, `visits`, `health`, `maxHealth`, `graceLeft`, `won`, `width`/`height` (for sizing BFS arrays only), `isKnown`, `knownTile`, `knownFloorCount`, `legalMoves`, `availableMoves`, `visibleAdversaries()` (`{ id, pos, mode, distance }` of the ones in sight now), `seenTreasure()` (the chest once lit, else `null`) and `move(dir)` (the explorer's own step).

**`src/characters/explorer/{known-map,encounter,perception}.js`**: the only source of text Jev reads about the world. Every function takes a `KnownWorld` (`world`).
- `known-map.js`: cell arithmetic, `knownDistances` BFS, `isFrontier`, `wouldReveal`, compass words. Imports no explorer file.
- `encounter.js`: the encounter model below plus `encounterFacts`, `knownLineOfSight`, `speedPhrase`. Imports known-map.js and `ADVERSARY_SPEED` from adversary.js, never perception.js.
- `perception.js`: approaches, tactic feasibility and options (they need `approachTarget`, hence they cannot live in encounter.js), `situation`, `avoidZone`, `describeMoves` / `describeMoveParts`.
- `APPROACHES` (each with `text` and a first-person `thought` ≤ 60 chars for the UI bubble):
  - Exploration: `nearest_frontier` (default), `largest_unexplored`, `far_side`, `collect_coins` (only while a lit pile is reachable; `approachTarget` picks the seen pile with the best coins per known-path step, never through the portal, skipping the avoid zone while another pile exists; when none is left the brain switches back to `nearest_frontier` with a `policy` record), `go_to_exit` (only once the portal is known; code commits to it on first sighting; reviews never replace it). `availableApproaches` lists only these.
  - Encounter **tactics** (`tactic: true`, `TACTICS`, `isTactic`): `slip_past`, `run_away` (the old `escape`), `engage` (close in and fight; replaced `face_off`, which is gone), `hide`, `race_to_exit` (portal seen), `carry_on` (every visible adversary patrolling).
- `situation(world, { remembered, landmarks })` returns the per-tick facts in three groups (the brain adds the rest of Jev's state, see below):
  - `self`: `{ lives, max_lives, hit_protection_steps, coins }` (`coins` = `world.coins`, its own purse).
  - `surroundings`: `{ here, steps, known_floor_cells, exit, unexplored_by_direction, frontier_cells, landmarks[] }`. `exit` is a sentence (`'not seen yet'`, `'seen, N steps away by known path'`, ...). `landmarks` are `memory.landmarks` made relative to the explorer each tick (`{ kind, note, direction, distance, steps_ago }`). `coins` (only while a pile is seen) lists the 3 nearest lit piles as `{ direction, distance, count }`.
  - `threats`: `{ visible[], remembered[], encounter }`. `visible` is `{ id, direction, distance, chasing, hp }` per adversary in sight now (`hp` = `'1 of 2 hp'`, its health bar). `remembered` is the brain's frozen sightings not in sight now, as `{ id, last_seen_steps_ago, was_chasing, hp, direction, distance }` (hp as seen then) measured from where the explorer stands (direction `'here'` on the frozen cell).
  - `known_floor_cells` is a **count**, not a percentage, because a percentage would leak the map size.
  - Unexplored amounts use a fixed 12-cell window (`SURVEY_REACH`) and fixed bins, independent of map size.
  - `threats.encounter` is `null` unless an adversary is visible. Otherwise it holds **sentiment-free** sentences: `space` (open room W×H with known ways out, corridor, junction or dead end), `adversaries`, `gap_now` (number), `speed` (from `ADVERSARY_SPEED`), `slip_past` (best route past and its closest approach), `hide`, `run_away`, `dead_ends`, and `chest` (only once seen).
- Encounter model (encounter.js; all over known floor and visible adversaries only):
  - After the explorer's `i` steps, an adversary may have taken `ceil(i·ADVERSARY_SPEED)` steps. The predicted gap at a cell is its known-path distance from the adversary (Euclidean fallback) minus that.
  - `safeDistances(minGap)` is a BFS that only enters cells keeping that gap. The portal may always be entered, since stepping onto it ends the game.
  - `routeSurvey` runs it for gaps 6..1. The largest gap at which a goal is still reachable is that route's closest approach.
  - A slip goal is a frontier cell (or the seen portal) within 60° of the adversary's bearing and at least as far away as the adversary.
  - A hide cell is within 10 steps and out of `knownLineOfSight`, a copy of the supercover walk in which **unknown cells block**.
  - `engage` (`engageTarget`) is offered only while a sword (attack skill) is ready (`armed`), for every mood, and **ignores the minimum gap**. The explorer acts first in a tick and a hit stuns, so walking up to a hunting ghost hands it the first claw (a stubbed duel: 12 hits in 20 walking in, 0 holding): against a ghost it has not stunned the target is a cell 2 known-path steps off (`HOLD_GAP`; its own cell when already there), so the ghost steps in and the sword strikes first; against one its own strike stunned less than `stunTicks` steps ago (`stunned`, the brain's `#struck` record: its own action, fog-safe) the target is a cell next to it; already next to one, its own cell (strike now). Cheapest target first, the weaker adversary on a tie. Its fact names the adversary and its hp and says the fight in numbers (`fightFacts` in encounter.js, from the visible hp and the sword's damage only): "N strikes dispel it; expect at most one claw at you." (the claw clause only up to 2 strikes, with one adversary in sight and `fight.steady`, i.e. `stunTicks` >= 2 and the sword's cooldown below it: measured by the stubbed duels in `check-skills.mjs` section 12, 24 ghost placements: 2 strikes dispel a 2 hp ghost, holding the 2-step gap takes 0 claws, walking in at most 1 and always before the first strike, never one between the first and second strike; a review stress run gave 2 claws with two ghosts, a sword cooldown of 3 or 6 against stun 2, or no stun with `clawCooldown` 0 and grace 0). Every engage fact explains that dispelling permanently removes that enemy and its pursuit; it never claims a clear-all win. Its moves are described with a gap of 1, it has its own safety line ("Never step onto an adversary"), and it never fails by gap.
- `tacticFeasibility(world, minGap, { exclude })` returns `{ id: { target, fact } }` for the feasible tactics only (a tactic whose target is in `exclude` is dropped). `tacticOptions` turns that into Choice criteria. `run_away` is always feasible while anything is visible.
- `approachTarget(world, id, { minGap, goal, avoid, exclude, remembered })`: `goal` keeps a tactic's earlier target cell while it is still reachable at the gap, so `slip_past` doesn't lose its goal once its own light reveals it. `exclude` (a Set of cell keys) rules cells out as targets (the brain fills it after a ping-pong). `remembered` is the brain's frozen sightings; `run_away` uses them when no adversary is in sight.
- `run_away` (`escapeTarget` in encounter.js): the escape spot is **sticky**, kept until it is reached or no route keeps a gap of 2 (`ESCAPE_KEEP_GAP`) from every adversary. A new one is picked among the cells reachable while keeping the mood's `min_gap` from every adversary (then 2, then any known cell; a tier counts only if it holds a spot at least 4 steps away, `ESCAPE_TRAVEL`), preferring cells on the edge of the known map and corridor/junction cells beyond a room exit over a corner of the room. While the adversary is out of sight it keeps the goal, and once the goal is reached it continues from the frozen chasing sighting (the 3 latest, up to 15 steps old). So `run_away` can have a target with no adversary visible.
- `approachTarget` also takes `avoid`, a Set of cell keys from `avoidZone(world, remembered)` (known cells within 10 known-path steps of a sighting younger than 10 steps, or within 6 of one up to 15 steps old, plus, for each of the 3 latest chasing sightings, a sector: the known cells nearer to the sighting than the explorer is, and the cells whose shortest route from the explorer runs through the frozen cell, within 2 steps). Exploration approaches skip frontier cells in it while any other frontier cell exists; tactics ignore it.
- `describeMoveParts(world, approachId, { minGap, goal, avoid, remembered, prev, backAndForth })` returns, per legal move, `{ shared, target }` (or `{ whole }` for a move that wins the game or for `stay`). `shared` holds the facts that do not depend on the approach: threats (with "below your minimum gap of N" when it applies), a sentence about the nearest remembered sighting ("Heads toward where an adversary was last seen N steps ago ...", and, for a chasing sighting up to 15 steps old, however far the spot is, when no sighting lies within 8 steps of the move's destination, "Heads back toward where a chasing adversary was N steps ago (D steps from that spot after this)."), chest, reveal estimate, visits, "Goes back to the cell you left 2 steps ago (back-and-forth N times in the last 6 moves)", dead-end and cornered warnings. `target` is progress toward this approach's target. `describeMoves` joins the two into one sentence per move. Only the 3 most recent remembered sightings get a BFS per call.
- **Shared move facts.** On a decision tick the brain asks one `move_if_<tactic>` question per feasible tactic. The tactic-independent `shared` facts are sent once, in `surroundings.moves` (`{ dir: sentence }`), and each option carries only its own `target` part, so the request does not repeat them per tactic. Ordinary ticks put the whole sentence in the `next_move` options and send no `surroundings.moves`.
- Distances to adversaries use a BFS over known floor when the adversary's cell is known; otherwise rounded Euclidean.
- Determinism: tie-breaks are steps, then `(y, x)`. Keep them.
- Performance:
  - BFS uses flat `Int32Array`s, and `describeMoves` runs several of them per call.
  - A decision tick runs about 6 gap-limited BFS per minimum gap. That is a few ms on 90×90 maps.
  - Don't add full-grid scans per candidate move.
- `check-dungeon.mjs` covers this with twin tests (encounter facts plus tactic options and targets for the bold and wary gaps, with hidden tiles and hidden adversaries scrambled, and remembered-sighting twins that move a hidden adversary after it was seen), hand-built slip/corridor/blocked-exit/hide maps, and a stub-Jev brain run (`new ExplorerBrain(world, { ask, memoryDir })`) that also asserts the state keys, the memory shape and the request-size bounds. Section 4f runs a smart stub Jev (it reads the move sentences the way the priorities say): under `run_away` in a 12x5 room the explorer returns to the cell it just left at most 2 times in 15 ticks, and after `chase_over` on a hall it doesn't walk back toward the frozen sighting while another frontier exists. It takes about 18 s.

## Adversaries & the tick

**Spawning** (`spawnAdversaries`):
- Seeded by `rng(seed ^ 0x9e3779b9)`.
- Count is `min(MAX_ADVERSARIES, max(1, round(floorCells/FLOOR_PER_ADVERSARY)))` (defaults 150 and 12; `MAX_ADVERSARIES = 0` means none), so it grows with the map: 2 on a 25×29 map, about 11 on 70×76.
- Adversaries spawn on room floor at path distance ≥ 20 from the start and outside the start's sight, spread round-robin across rooms (maze layout).
- **Linear layout** (`dungeon.layout.kind === 'linear'`; same count formula, same rng stream and the same distance and sight rule): the portal room always gets one, each side room a guardian with chance 1/2 (at most half of the monsters left after the portal guard, so a 2-3 monster map still has some on the path), and the rest spread over the main-path rooms, denser toward the portal; none in the start room. Checks: `scripts/check-linear-spawn.mjs`.
- Built as `new Adversary({ id: 'a1', pos, character })`; `character` is a preset id from `character.js` and defaults to `'standard'`, so a hand-built `new Adversary({ id, pos })` still works. Public shape (and JSON, in this order): `{ id, pos, mode: 'patrol', budget: 0, lastSeen: null, goal: null }`. **Don't add public fields.**
- Private state (`#hunt` brain state from `brain.js` `newHunt`, `#route` the patrol route, `#lastRequestBody`, `#character` and its derived profile and home cell) is reached through prototype accessors `hunt`, `memory`, `route`, `lastRequestBody`, `lastRequest()`, `character`, `profile` and `home`, which are not own properties, so JSON, `Object.keys` and spread still show exactly six keys. Never spread or JSON-clone an `Adversary`.
- **Kinds** (`kinds.js`): what a monster *is* (`ghost`, `troll`), apart from its character (personality). `KINDS[id]` holds the per-kind attributes (`hp`, `skills`; later lives, speed, traits). The troll hunts and decides like a ghost but has its own numbers: `trollHp` 4 (a ghost has 2), `trollClawDamage` 2 (a ghost claw takes 1; with 2 lives one troll claw ends the game), `trollSpeed` 0.65 (a share of `ADVERSARY_SPEED`, read as `Adversary.speed`; Skills settings, `next`). A kind row has `hp()`, `speed()`, `skills` and `tuning()` (per-loadout overrides, applied only to the kind's own loadout). Explorer-side speed predictions still use the plain ghost speed (conservative). The troll sprite has a 4-frame walk cycle (`ART.troll.walk`, feet lift alternately) played for `WALK_MS` after each step in `app.js`. `Adversary` takes `kind` (default `ghost`; private `#kind`, accessor `kind`, no new public field), and `hp` / `skills` default from the kind. Spawn draws kinds with `assignKinds(seed, count, trollShare)` on its own stream (`seed ^ 0x7f4a7c15`) after all spawn rng calls, one draw per monster, so cells and dungeons never change. Setting `trollShare` (Spawn, default 0.25, `next`). Testbed `kinds`: `'ghost'` (default), `'troll'`, `'mixed'` or a cycled list. `view().adversaries[].kind` drives the sprite in `app.js`. Explorer requests say "enemy", so a kind never reaches Jev from that side.
- **Enemy levels** (PLAN-levels; `kinds.js`, `adversary.js`, `explorer/encounter.js`). Every monster has a **level 1-3**, fixed at spawn: `LEVEL_RANGE = { ghost: [1, 2], troll: [2, 3] }` (a constructor or the testbed may give any 1-3; the draw stays in range). `assignLevels(seed, kinds)` draws on its own stream (`seed ^ 0x3c6ef372`), one draw per monster in id order, after the kind stream and drawn even with levels off, so dungeons, spawns and kinds never change; uniform within the range unless `weights` say otherwise (all-zero weights = even). `levelStats(kind, level)` -> `{ hp, clawDamage }` = `max(1, round(base * mult[level]))` with defaults `hpMult [0.5, 1, 1.5]`, `dmgMult [1, 1, 1.5]`: ghost L1/L2 = 1/2 hp, claw 1/1; troll L2/L3 = 4/6 hp, claw 2/3. Level 2 is today's base; speed and stun never change. `Adversary` takes `level` (default `defaultLevel(kind)`, 2 clamped into the range; a bad level throws), with private `#level` / `#clawDamage` behind accessors `level` and `clawDamage` (still six public keys); the claw skill it was built with is scaled by `clawMult(level)`. **Fog:** `level` and `clawDamage` are in-sight reads like `hp` (rule 1), frozen in `#seen` sightings; Jev gets `level` and `claw_lives` beside the health bar in `threats.visible[]` / `threats.remembered[]` (levels on only). **Matchup** (`encounter.js` `matchup(world, th, damage)` -> `'weak' | 'even' | 'too_strong'`): `strikes = ceil(hp / swordDamage)`, `claws = ceil(lives / clawDamage)`; `weak` = strikes 1 and claws > `cautionClaws`; `too_strong` = claws <= `cautionClaws` and strikes > 1; else `even`. Levels off, or no level on the record: always `even`. `engageTarget` skips a `too_strong` threat unless the explorer is cornered (the corner model's verdict, or the caller's `cornered` flag); `fightFacts` adds a "weak target" line for a `weak` one. On the first sighting of a `weak` / `too_strong` monster the brain sets `ExplorerBrain.remark` (shown in `view().explorer.remark`, null otherwise): the next line of `remarkLine(kind, n)` from the pool (`ui.thoughts.explorer.weak_target` / `.too_strong` text knobs; defaults "Ah, that's a weak target." / "I don't have enough health to fight this guy."), deterministic, no rng. **Knobs** (central config `monsters.levels.*`, file-only, next game): `enabled` (default true; false = every monster level 2, today's stats and request bytes), `hpMult`, `dmgMult` (3-tuples), `weights.ghost` / `weights.troll` (2-tuples, low to high level), `cautionClaws` (default 1). `view().adversaries[]` carries `level` and `claw_damage` (Reveal-only display; the UI draws a pip badge, fog-gated like the hp bar). Testbed `levels` key: see Testbed. Checks: `check-levels.mjs` (explorer side), `check-config.mjs` section 9 and `check-kinds.mjs` (draw, stats, knobs).
- **Characters** (`character.js`, plan section 1). Five traits at levels 1-3 (`aggression`, `persistence`, `horizon`, `roaming`, `pack`; `caution` is reserved and dormant), nine presets (`standard`, `aggressive`, `pursuer`, `ambusher`, `patient_hunter`, `short_sighted`, `timid`, `territorial`, `rover`), and `profileOf(traits)`, one pure function that returns every number a ghost uses (chase range, rest ticks, search ticks, keep-hunting threshold, sweep radius, cut-off window, home radius, alert reach, call and team-sight flags, memory sizes and ttls, the priority line and the words sent to Jev). `standard` follows the live settings values, so the settings page still tunes it; every other character uses its profile numbers (and only an `aggression` 1 ghost rests after giving up; levels 2 and 3 do not). A character is fixed at spawn and never re-picked. With the `adversaryCharacters` toggle off, every ghost is `standard` and requests are byte-identical to the pre-character code (checked against a request-hash baseline). The testbed `characters` key sets them per ghost.
- **Spawn assignment.** With `adversaryCharacters` on, `spawnAdversaries` assigns characters with `assignCharacters(seed, count, 'mixed')` on its own stream (`rng(seed ^ 0x6a09e667)`) **after** all spawn `rng()` calls, so ghost cells and dungeons are unchanged (rule 8; `check-characters.mjs` proves it over 30 seeds). The deck is the eight non-standard presets in shuffled order; ghost *i* gets deck entry *i*, independent of how many ghosts exist.
- **Patrol RNG.** Toggle off: the patrol RNG (`seed ^ 0x85ebca6b`) is `game.patrolRand`, one stream per game, created on the first patrol goal. Toggle on: one stream per ghost, `rng(seed ^ 0x85ebca6b ^ hash(id))`, so one ghost's draws never shift another's (patrol routes change, dungeons do not). A ghost with a finite `homeRadius` (non-standard characters) picks patrol goals only from rooms within that many path steps of its spawn cell plus its spawn room; only the candidate list shrinks, so the number of `rand()` calls per goal is unchanged.

**Constants** (adversary.js:14-27) are `export let` defaults that `src/settings.js` changes through `configureAdversaries()` (importers see the live value): `ADVERSARY_SPEED = 0.6` (3 steps per 5 ticks), `CHASE_RANGE = 7`, `MAX_SEARCH_TICKS = 18`, `GRACE_TICKS = 4`, `ALERT_STEPS = 24`. Private tunables in the same file: `FLOOR_PER_ADVERSARY = 150`, `MAX_ADVERSARIES = 12`, `PACK_ALERT = true`, `TEAM_SIGHT = true`; `MIN_SPAWN_STEPS = 20` is fixed. `KEEP_HUNTING_MIN = 0.5` lives in `adversary/brain.js` (also settable). `SIGHT_RANGE` is in dungeon.js. The adversary rules text (`rules()` in `adversary/brain.js`) is built from the live `SIGHT_RANGE`, speed, `MAX_SEARCH_TICKS`, the ghost's claw damage (`clawDamage`, passed as `cfg.hitDamage`) and `GRACE_TICKS` (the last four arrive in `cfg`).

**Sight vs chase:**
- `seesExplorer` = Euclidean ≤ `SIGHT_RANGE` + LOS.
- `startsChase` = `seesExplorer && distance <= CHASE_RANGE`.
- They are kept as separate functions and constants on purpose (and are separate knobs on the settings page); see [Open questions](#open-questions--known-issues).

**Modes:**
- `patrol`: brain off, code wander, no Jev.
- `chase`: brain on, explorer in sight.
- `search`: brain on, no sight.

**Transitions:**
- `startsChase` emits `spotted` then `brain_on`, then (when `PACK_ALERT` is on) `alerted` + `brain_on` for each patrolling packmate within `ALERT_STEPS` path steps (they join in search mode at the explorer's cell, heading as the spotter saw it; alerted ghosts do not alert further; `alertNearby` in adversary.js). `check-testbed.mjs` has a pack-alert scenario for this.
- **Team sight** (when `TEAM_SIGHT` is on): a hunting adversary counts as seeing the explorer when any hunting packmate does (`tracksExplorer`), so a pack closes in together. The adversary's `describeMoves` (`adversary/perception.js`, not the explorer's) adds a "Cuts off N of M cells" fact per move in sight (cells the explorer can reach within `COVER_RADIUS` = 12 steps where this ghost would arrive first, and how many no other ghost covers).
- While the brain is on, sensing flips the adversary between chase and search (`spotted` / `lost_sight`).
- The brain switches off (`brain_off` with `reason`, back to patrol) in either of two cases:
  - more than `MAX_SEARCH_TICKS` (18) ticks pass without sight;
  - Jev's `keep_hunting` answer comes back below `KEEP_HUNTING_MIN`.
- **No `gave_up` event is ever emitted** (the adversary's own memory does log a "Gave up: reason" event, see below).

**Adversary fog of war** (rule 1 extended to ghosts by PLAN-adversary-memory.md A1/A4; the plan's extension of rule 1 is in force only behind the `limitedMap` toggle, which is **off by default** and acts only together with `adversaryCharacters`; `limitedActive()` in adversary.js):
- **Default (`limitedMap` off):** adversaries know the real map, through an `AdversaryView` in `full` mode. Adversary perception, brain and memory code reads the world only through that view, never a `Game`.
- **`limitedMap` on:** a ghost knows only the set K of its `AdversaryView` (`limited` mode): its **home zone** (the whole spawn room plus every floor cell within `homeRadius` path steps of its spawn cell; 14 / 24 / whole map by `roaming`; computed once in the constructor, the only read of the real geometry, never expires), the cells it has **seen** (line of sight within `SIGHT_RANGE` from every cell it stood on, stamped with the tick, forgotten after the character's `seenTtl`, oldest evicted at `seenCap`), cells **heard** (on a call, the caller's own known cells within 6 path steps of the reported cell, copied from the caller's K, not the real map), and the four cells around it. A wall is known only when 8-adjacent to a known floor cell. BFS, `cellKind`, sweep and cut-off targets, patrol goals (known rooms within `homeRadius`) and `path_steps` all run over K; a spot with no known route gets `path_steps: null` and the brain heads for `frontierToward(cell)`, shown as "the edge of what you know". The state carries `surroundings.map_note` and the rules text has the fog line instead of "You know the whole map".
- Both modes: they know the explorer's position only while `seesExplorer` is true (or, with `TEAM_SIGHT`, a hunting packmate sees it). Otherwise they know frozen `last_seen` / sightings only. They never know the treasure or what the explorer has explored (light, visits, trail).
- Views update sequentially in id order before any ghost senses or decides, and `buildRequest` stays synchronous.
- **Static guard** (`check-dungeon.mjs` section 0b): `adversary/{perception,brain,memory,character}.js` may not use `game.x`, `game[...]`, `.dungeon`, dynamic or namespace imports, or import beyond an allowlist (`DIRS`, `SIGHT_RANGE`, `rng` from dungeon.js, `ADVERSARY_SPEED` from adversary.js, sibling adversary files, `shared/memory-kit.js`, jev.js). `adversary.js` (physics, touch checks, spawning, `alertNearby`) and `adversary-view.js` are exempt, like `known-world.js` for the explorer. The explorer guard also allows `../shared/memory-kit.js`.
- **Fog twins** (`check-adversaries.mjs`, limited mode): a twin game scrambles tiles outside K and not 8-adjacent to it, the chest, the hidden explorer, packmates out of hearing and the explorer's visits/trail; the ghost's request must be byte-identical (patrol, chase, search, alerted from far, `last_seen` outside K). Plus a fading/cap test and a scan that no coordinate outside K appears in a request.

### Adversary memory & Jev state

`adversary/memory.js` (`createMemory(id, character)`, validated by `validateMemory`, all memories written together to `adversaries.json` as `{ tick, adversaries }` each tick). One per `Adversary`, reached as `a.memory`:

```
{ id, character { id }, objective, brain { on, since_tick, last_reason },
  approach { id | null, current, since_step, tried[{ id, steps, reason }] },
  tally { sightings, lost_sight, hits, alerts_heard },
  events[{ tick, text }],
  progress { ticks_hunting, ticks_since_seen, distance_trend },
  latest_action: null | { choice, confidence, forced, fallback },
  sightings[{ cell, tick, heading, source: 'seen' | 'called', by? }],
  recent { moves[], cells[], back_and_forth },
  landmarks[{ kind, cell, tick, note }],
  lifetime { hunts, escapes, hits, last_hunt_end_tick },
  morale: null | { value, baseline, tier, mood, counts } }
```
- `morale` is `null` unless the **`monsterMorale` toggle is on** (see [Monster morale](#monster-morale-plan-monster-morale)); it is a mirror of the private score, kept across hunts, and `brainOn` never resets it.
- The four fields `sightings`, `recent`, `landmarks` and `lifetime` are filled only while the **`adversaryCharacters` toggle is on** (`MEMORY_ON` in `brain.js`, set by `configureAdversaries`); with it off they stay empty and requests are unchanged. Units are world ticks. `character` is `{ id }` and is also shown in `view().adversaries[].character` (a Reveal-only display; the explorer never reads it).
- `sightings`: the explorer as it was when last in sight (own sight, team sight or a call), frozen, newest first, stored only when it moved at least 3 cells (`SIGHTING_SPACING`) from the newest one, so a chase is a trail. Kept 1 / 3 / 5 by `horizon`, dropped after a ttl of 12 / 30 / 60 ticks. `a.lastSeen` stays for the public shape and the brain-on/off code.
- `recent`: the ghost's own last moves and cells (`backAndForth` from the shared kit); three ping-pongs while searching force a `search_approach` re-pick.
- `landmarks` (kinds `home` (pinned), `explorer_seen`, `explorer_lost`, `explorer_hid`, `hit_here`, `area_checked`; one per kind + cell, capped 3 / 5 / 8 by `horizon`, ttl 40 / 120 / 300 ticks): **`chest` is not a legal kind** and validation throws on it, because a ghost never knows the chest.
- `lifetime` is never reset by `brainOn` / `brainOff`; `escapes` counts hunts ended by timeout or `keep_hunting`. With the toggle on, `events` are kept across hunts (not cleared by `brainOn`) and aged out by ttl; `tally` still resets per hunt.
- `tally` and `events` (`findings` is gone) describe the **current hunt**: `brainOn` resets them. Events (≤ 5, oldest dropped, an identical repeat ignored, the tick never repeated in the text): first sighting, "called for help" (alerted), "Hit the explorer (hit N)", "Gave up: reason". The tally counts `sightings` (re-sights), `lost_sight`, `hits`, `alerts_heard`.
- `approach.id` is `null` exactly while the brain is off. `tried` keeps only the outcome of a **search approach** (`cut_off`, `sweep_last_seen`) that was replaced by another search approach or by giving up. Hops between `direct_pursuit` and searching are not logged.
- `latest_action` is Jev's last `next_move` answer **without probabilities** (validation rejects the key): `{ choice, confidence, forced, fallback }`. The probabilities live in the private hunt state (`a.hunt.probabilities`) and `brainView(a)` (the browser's `view().adversaries[].brain`) still returns `latest_action: { choice, probabilities, confidence }`, so the UI is unchanged.
- Limits: events 5 (text 200), tried 5, approach 240, reason 200, trend 160.
- `noteHit(a, tick)` (`adversary/brain.js`) is called from `strikeWith` in adversary.js when a claw strike takes a life: it bumps `tally.hits` and adds the event. A bump never calls it.

The request body (`jevState` in `adversary/brain.js`) is `{ game, tick, self, surroundings, explorer, last_seen, [approach_target, checked_cells_near_last_seen], team, recent }`:
- `self` = `{ id, position, mode ('chase'|'search'), approach, latest_action }`; `surroundings` is map facts around the ghost.
- `explorer` carries a position, direction, `path_steps` and `heading` **only while in sight** (else `{ in_sight: false }`); `last_seen` is `{ cell, ticks_ago, heading, direction, path_steps }` or `null`.
- `approach_target` and `checked_cells_near_last_seen` (`"N of M floor cells within 10 steps"`) appear only while searching.
- `team` lists the other ghosts as `{ id, direction, path_steps, role: 'pursuing'|'searching'|'patrolling' }`; `recent` = `{ tally, events, progress }`.
- **Memory mode** (the `adversaryCharacters` toggle on) regroups the state: `self` gains `character { id, traits (words, never numbers), style }` (a non-standard ghost gets it even with the toggle off); `surroundings` gains `landmarks[]` (direction, `path_steps`, `ticks_ago`, a fresh/stale/cold word) and, in limited mode, `map_note`; `explorer` gains `sightings[]` (`ticks_ago`, freshness word, direction, `path_steps | null`, heading, source) and a `trail` sentence out of sight; `team` lists only packmates this ghost can hear (within its alert reach by path) or see, the nearest 4, each with the freshest report from its own sightings (`source: 'called by aN'`, direction, `path_steps`; never a cell), plus `{ others: N }`; `recent` = `{ path { moves, back_and_forth }, tally, lifetime, events, progress }`. The rules text is shorter. A non-standard ghost's priority line (at most 300 characters) is the third `next_move` priority and a clause in `search_approach` / `keep_hunting`; a standard ghost's request text is exactly the pre-character text. `last_seen` is still sent. Request size with memory on is asserted by `measure-memory --who adversary`: average ≤ 5.5 KB, max ≤ 8 KB (measured about 4.6 KB / 7.3 KB over 10 seeds at the time A3 was built).
- Questions: `next_move` (not asked with a single legal move or when a move catches the explorer), `search_approach` (first search tick: `cut_off` vs `sweep_last_seen`), `keep_hunting` (Noul, every search tick).

### Damage (strikes, grace, bumps)

Code: `bumpCheck`, `knockBack`, `strikeWith`, `graceLeft` in adversary.js; `resolveAttack` in `src/skills/resolve.js`; `Game.damage` in dungeon.js. Numbers below are the defaults (`GRACE_TICKS`, the Skills settings).
- **A touch is a bump.** An adversary on the explorer's cell (it stepped in, or the explorer stepped onto it) is knocked off it and emits `{ id, type: 'bump', at }`. No life is lost and no grace starts. Patrolling and hunting ghosts alike. The claw's damage is the `clawDamage` skill number (the old `hitDamage` setting and `HIT_DAMAGE` are gone; an old settings file that still has it loads fine, the key is skipped).
- **A strike takes the life.** Only a hunting ghost (brain on) uses its claw strike; a patrolling one never strikes. `strikeWith` calls `resolveAttack`, which, when the explorer stands in a strike cell, rolls the explorer's block (`game.skillRand`), then the grace and latch gate, then calls `game.damage(damage, a.id)` and emits `{ id, type: 'hit', at, health }` (health after the hit). The life-ending hit also emits `{ id, type: 'caught', at }` right after its `hit`, and `stepAdversaries` returns at once.
- **One hit per tick.** Grace is read once at the start of `stepAdversaries` (`protectedNow`) and a per-call `hit` latch (`canHit()`) blocks a second hit in the same tick. A strike that lands on a protected or already-hit explorer still flashes, with result `protected`.
- **Grace.** A hit sets `game.graceTicks = GRACE_TICKS` (4). Each `stepAdversaries` call starts by reading and then decrementing it, so the next 4 ticks cannot hurt; the 5th can. `graceTicks` is a `Game` field (0 from the constructor); `graceLeft(game)` reads it.
- **Knockback (bump).** Any adversary on a living explorer's cell after a bump check is moved off it, so a ghost never ends a tick inside the explorer. An adversary that just stepped in goes back to the cell it came from; one found there before moving (the explorer stepped in) goes to the first floor neighbour in `DIRS` order that is not the explorer's cell, preferring one that is not the explorer's previous trail cell; boxed in, it stays. Knockback clears the patrol route but **keeps the ghost's `budget`**: a bump must not cost the ghost its next act, or an explorer stepping onto a ghost every tick (a 1-wide corridor) would bump-lock it and the ghost would never strike (`check-adversaries.mjs` reproduces the corridor). Only a *strike's* knockback (`Adversary.takeHit`, see Skills) sets `budget = 0` and stuns. No `rng()` is used.
- **Known consequence.** A brain-on ghost's step onto the explorer is no longer forced (it only bumps); a ghost next to the explorer with its claw ready may strike instead. Standing next to a ghost is still not safe.
- **Explorer text.** `situation.lives` (= `world.health`) and `situation.hit_protection_steps` (= `world.graceLeft`) are the explorer's own state, so fog-safe. The step-into move fact is `Steps into the adversary: only bumps it back, no life lost.` (`bumpSentence` in perception.js). A life lost to a strike adds an event, a `hit_here` landmark and an `encounters.hits` count via `ExplorerBrain.noteHit` (called from `Run.playTurn` when a `hit` event fired); the lethal one keeps `noteCaught`. The explorer's `rules()` says "A touch only bumps. An adjacent adversary's claw costs C life/lives (you start with N; at 0 you lose); after a hit you are safe for G steps." (C = `clawDamage`).
- **Adversary text.** The ghost's `rules()` (`adversary/brain.js`) says touching is harmless and only its claw strike hurts: the explorer loses `clawDamage` and cannot be hurt for `GRACE_TICKS` after a hit. The "Steps onto the explorer" move fact says it only bumps.

**`stepAdversaries(game, { decide })` order** (adversary.js; `decide` replaces the Jev call, null = the real one). These invariants are easy to break:
1. Return immediately if the game is won or lost. Read grace (`protectedNow`), then decrement `game.graceTicks`.
2. Sort adversaries by id. Each stunned ghost loses a stun tick (`tickStun`). Run the bump check for each **before anything moves**: this knocks back a ghost the explorer stepped onto. Nothing is lethal here.
3. Advance the tick counter (`game.adversaryTicks`), update the views, and run `senseStart` for each.
4. Add `ADVERSARY_SPEED` to every budget, except a stunned ghost's (it gains none). An adversary moves at most one step per tick.
5. Adversaries with `budget >= 1`, the brain on and no stun call Jev **in parallel**, all from the same post-explorer snapshot. A stunned ghost makes no call.
6. In id order, for each ghost that acts: **skill, then step, then bump check.** A hunting ghost whose answer is a `skill` key (at or above `SKILL_MIN`) runs `strikeWith` first; a lethal strike returns at once. Then the step (a failed Jev call falls back to a code BFS move with `console.warn`; brain-off ghosts take a patrol step and never strike), then the bump check (knockback to the previous cell), then `skills.turnPassed()`. Two adversaries may share a cell, but never the living explorer's.
7. Return `{ events, turns }`. Every turn has `skill_decision` (`null` or `{ choice, probabilities, used }`, API/browser only) and may carry `stunned`.

**`src/turn.js`** (`Run`):
- `newGame(seed?, opts)` generates, spawns and returns a `Run`; `newTestGame(config, opts)` does the same for a testbed arena. Constructing one costs no Jev calls.
- `run.playTurn()` runs `run.explorer.takeTurn()`, then `stepAdversaries(game, { decide })`, then `saveMemories(..., dir)` (writes `adversaries.json`), then `explorer.noteCaught` if the game was newly lost, else `explorer.noteHit` if a `hit` event fired. The explorer's turn, including its memory save, finishes before the adversaries start. Adversary brains build their request bodies synchronously, in id order, because the option shuffle uses `Math.random`: don't add an `await` before `buildRequest` in `adversary/brain.js` `decide`.
- `run.memory` is the explorer's plain-JSON memory (`run.explorer.memory`).
- `run.view()` sends the **full** adversary list, each as `{ id, pos, mode, visible, brain }`, plus `grace_ticks` and `invulnerable` (grace > 0). The UI hides adversaries that aren't visible unless Reveal is on.

## Skills (attack and block)

Built from PLAN-skills.md (S1-S5; the plan is a plan, this is the code). Skills ride on the existing request: they add bytes, not calls, on a normal tick. See CONTRACT.md for signatures.

- **Classes** (`src/skills/`). `Skill` (stateful: cooldown, uses; `options(view, self)` returns `[{ key, fact, target }]`; `summary()` is the plain-JSON mirror `{ id, kind, name, text, ready, cooldown_left }`), `AttackSkill` (a `shape` of `[forward, right]` cells, rotated to the aim by `cells(pos, facing)`; `damage`), `BlockSkill` (`effectiveness` 0..1), `SkillSet` (**at most 4** skills, duplicate ids throw; `options()`, `get(key)`, `summaries()`, `turnPassed()`). A new behaviour (sweep, cone, radius) is a subclass registered in `KINDS` in loadouts.js.
- **Loadouts** (`loadouts.js`, data): `sword_strike` (attack, damage 1, cooldown 1 step), `shield_block` (block, 0.6, cooldown 2 steps), `fire_strike` (area, damage 2, cooldown 120 steps), `dash` (movement up to 4 cells, cooldown 20 real seconds), `claw_strike` (attack, damage 1, cooldown 2 steps). `buildSkillSet('explorer' | 'ghost' | 'none' | [ids])`: the explorer gets sword, shield, fire strike and Dash, a ghost the claw only (no block). Numbers come from `config.js` (`skillConfig()`, fed by `settings.js` through `configureSkills`); read them again after a change, never cache.
- **The `skill` question** (`question.js`). One Choice per request, never per tactic and never in the sentiment call. `none` is listed first and not shuffled. The explorer asks it with neutral wording (`skillQuestion(..., { neutral: true })`: "Use at most one skill this step, besides the move."), so its mood's `skill_priority` decides; ghosts keep the original "Choose `none` unless a skill clearly helps" wording (their requests are unchanged). `pickSkill` returns the chosen key only when its probability is at least `SKILL_MIN` (0.5), else `none`. The aim is part of the option key (`sword_strike_left`), so it never depends on the move answer. The explorer's `skill_priority` line per mind (in `SENTIMENTS`) goes into the question and into `next_move` priorities while a skill is offered.
- **The gate** (loose, plan D7). The explorer's brain (`#skillOptions`) offers options only when a skill is ready and an adversary is visible within `SKILL_NEAR = 10`, or a sighting up to 10 steps old lies within 10. The attack lists one option per aim whose cells hold a **visible** adversary (stricter than "every aim"), so it can be empty while the gate is open. The block is offered when a visible chasing adversary is within `THREAT_STEPS` path steps. `GHOSTS_CAN_ATTACK = true` in brain.js keeps the block offered. A ghost asks only with the explorer in sight within 10 cells (`skillOptionsOf`).
- **Forced ticks.** With one legal move and a skill offered the brain sends a skill-only request (the D4 path). It is dormant for the explorer: `availableMoves()` always includes `stay`, so a forced tick never happens. A ghost with one legal move does send it.
- **Resolution order.** The explorer's skill resolves **before** its step: `ExplorerBrain` calls `world.useSkill(skillSet, key)`, then `world.move(dir)`, then `skills.turnPassed()`. A ghost's is skill, then step, then bump check (see `stepAdversaries`). `game.clearTickState()` runs at the start of `Run.playTurn`: it empties `game.strikes` and lets a lapsed block go.
- **`resolveAttack(game, attacker, cells, damage, { canHit, onHit, rand })`** (`resolve.js`) drops wall and off-map cells, then: a ghost's strike on the explorer's cell checks the block (a roll of `game.skillRandom()` below `game.block.effectiveness`, while `game.steps <= game.block.until_step`) to give `blocked`, else the grace/latch gate (`protected`), else damage (`hit`, `caught`). An explorer's strike on a ghost **always lands** (no roll): `Adversary.takeHit` loses hp, and unless that was the last hp the ghost is knocked 1 cell away from the attacker and stunned `stunTicks` ticks (no step, no Jev call, no budget). At 0 hp the ghost is **dispelled**: removed from `game.adversaries` in place (so `team()`, pack alert and `adversaries.json` drop it). Every strike is pushed to `game.strikes` as `{ by, cells, result }` (`hit`, `blocked`, `protected`, `miss`, `dispelled`).
- **Block roll RNG.** `game.skillRandom()` uses `game.skillRand`, created on the first roll from `seed ^ 0x2545f491`. It never touches the dungeon or spawn `rng()` order (rule 8).
- **Ghost state** (private, behind accessors, so JSON still shows six keys): `skills`, `facing`, `hp`, `maxHp`, `stun`; `takeHit()` and `tickStun()`. Constructor: `new Adversary({ ..., hp = ghostHp setting, skills = 'ghost' })` (a SkillSet, a loadout list or a set name). `Game.facing` is the explorer's (last step's direction or last strike's aim).
- **Fog rule for skill facts.** Explorer skill facts use only `visibleAdversaries()` (which carries the health bar, `hp` / `maxHp`, of each adversary in sight) and the brain's own sightings. The strike option says what it does: `Strike to your left: a1 (2 of 2 hp) is knocked back and stunned 2 steps.` or `... (1 of 2 hp) is dispelled for good (may drop a coin).` They never use a ghost's stun, cooldown or loadout, which `KnownWorld` does not expose. The brain drops a dispelled ghost from `#seen` (it saw it go). A ghost reads the explorer only through its view (position only in sight). `check-dungeon.mjs` holds a twin that scrambles a visible ghost's stun and skills and requires an identical request, checks that a different hp in sight does change it and that an unseen ghost's hp does not, plus a dispel twin; section 0c is the static guard for `src/skills/` (`options()` reads only its arguments).
- **Memory.** `memory.skills` is a mirror of `summaries()` (<= 4, `LIMITS.skills`, `skillText` 120), rewritten before every save (explorer: `#save`; ghost: `syncSkills`). Jev's state carries `self.skills` as a compact map `{ id: 'ready' | 'ready in N' }` (the rules sentence covers what the sword does) to stay inside the request bounds.
- **Events.** Explorer strike: `strike` (always), plus `struck` (a ghost lost hp, with `hp`) or `dispelled`. Ghost strike: `strike`, `blocked`, `hit`, `caught`. A touch: `bump`. The explorer's memory logs "Struck a1 with the sword." and "Dispelled a1.".
- **Fire strike** (`area.js` `AreaSkill`, kind `area`, so every `kind === 'attack'` lookup (`#armed`, `#fight`, `#combat`, the engage hold, confidence's `armed`) still means the sword only). A 9x9 block centred on the explorer (`BLOCK_9X9` = `squareBlock(9)`, 4 cells each way; an even size would be aimed by code at the placement holding the most visible enemies, ties in `DIRS` order), `fireDamage` 2 to every enemy in it, `fireCooldown` 120 steps, ready at the start. Offered as ONE option `fire_strike` (no aim in the key) only while ready, at least `minSeen` = 2 enemies in sight (outnumbered; one is the sword's job) and at least one of them inside the block. Its fact counts the outcomes from the visible health bars ("dispels 2, leaves 1 at 2 hp"), never names a kind or the coin chance, and calls it the best way to break out when outnumbered. Fog: `KnownWorld.useSkill` burns only the block's cells in real line of sight from the explorer (inside 2 cells that is "in sight"), so an enemy round a wall corner is never struck (twin in check-skills section 13); facing is not changed. The strike is recorded as `{ ..., skill: 'fire_strike' }` in `game.strikes` (the field is absent for every other strike), and the UI plays `ART.fire_strike` (18 frames, `FIRE_MS` 1490, knob `ui.fireMs`) on its own clock (`fireFx`) at `strike.centre` (the middle of the whole block, so walls that cut cells off do not shift it), at the end of Pass A (a floor-level effect: every wall, solid prop and character of Pass B covers it, and its struck-cell outlines skip the edge pass), instead of the slash. Before that step's view is applied, the explorer's bubble shouts "Fire Strike!" for `FIRE_CALL_MS` 550 ms (knob `ui.fireCallMs`), so the call comes before the blast while the enemies still stand. While the option is on the skill question, one clause (`FIRE_LINE` in brain.js: "Outnumbered with the fire strike ready: use it to break out or clear them at once.") follows the mood's `skill_priority`, because the low moods say "keep running" exactly when it is offered; not with a live directive. Knobs `skills.fire_strike.damage` / `.cooldown` (file-only, `fireDamage` / `fireCooldown`). Request size: an outnumbered decision tick (3 chasers in the block, sword + shield + fire options) is about 7.9 KB, measured in check-dungeon.
- **Settings** (Skills group in `src/settings.js`, all `when: 'next'`): `swordDamage` 1, `swordCooldown` 1, `shieldChance` 0.6, `shieldCooldown` 2, `clawDamage` 1, `clawCooldown` 2, `ghostHp` 2, `stunTicks` 2, `coinDropChance` 0.6 (see [Coins](#coins)). There are no on/off toggles. The testbed keys are `explorerSkills`, `ghostSkills`, `ghostHp`.
- **Adding a skill:** a loadout entry (and a subclass if it behaves differently), a `settings.js` row if it has tunables, a case in `check-skills.mjs`, and a look at the request-size bounds.

## Player directive (PLAN-inject)

The player can whisper one short instruction to the explorer. Built I1-I4 (PLAN-inject.md); it costs no Jev call by itself, only the following steps do.
- **API.** `POST /api/inject { text }` (relative `api/inject` in the page). `200 { directive, queued }`, `400` not JSON / not a string / over `injectMaxChars` after sanitising, `403` `injectEnabled` off, `409` no game or game over, `429` cooldown with `retry_in_ms`. Empty text clears (no cooldown). Policy lives in `Run.submitDirective(text, { maxChars, steps, cooldownMs, now })` (testable without HTTP); `sanitiseDirective` (turn.js) trims, collapses whitespace and strips control / bidi / zero-width characters. A step in flight queues the change (latest wins) and `playTurn` applies it at its start, so it never races `takeTurn`. A new directive replaces the live one.
- **Settings** (Player group, a Player tab on `/settings`, all `live`): `injectEnabled` true, `injectMaxChars` 140, `injectSteps` 20, `injectCooldownS` 10. The page reads them from `api/settings` on load and Reload; a 403 disables the form with the server's message.
- **Brain** (`ExplorerBrain`): `setDirective(text, { steps })`, `clearDirective(reason)`, getter `directive` (`{ text, from_step, until_step, steps_left }` or null), `memory.directive` (`{ text, from_step, until_step }`, validated, `LIMITS.directive` 140). Lifetime is in game steps. While live: `state.directive = { text, steps_left, from_step }`, one rules sentence, `plan.approach` shown as `directive` with the real approach parked (`interrupted`, reason 'player directive'), the first priority line of `next_move`, `tactic`, `move_if_*` and `skill` is `Follow the player's directive: "<text>". It outranks the mood and the approach. Never step onto an adversary.`, mood / approach lines and approach-target facts are dropped, and no `approach_working` / `next_approach` / `leave_now` / coin question is asked. A new directive queues a `directive` decision trigger (merged: still one sentiment call). Expiry or a clear resumes the approach with fresh counters and no `plan.tried` row.
- **Early end (I4).** `directive_done` (Noul) is added to an ordinary tick request at most every `DIRECTIVE_ASK_EVERY = 5` steps, never to the tactic request or a forced tick, so it costs no call. Above `DIRECTIVE_DONE = 0.5` the directive ends ("Directive ended: Jev judged it done.").
- **Events** (explorer memory): `Heard: <text>`, `Directive ended: <reason>` (ran out of steps, replaced by a new one, cleared by the player, Jev judged it done). `turn.directive` and `view().directive` carry the live directive (null otherwise); `POST /api/step` also returns `directive`.
- **Rules.** The text is the player's own, so fog of war is untouched; it is quoted in requests and cannot switch off the safety line. No `rng()` is used. With no directive requests are byte-identical (`check-request-hashes`). Checks: `check-inject.mjs` (brain, requests, expiry, `directive_done`, size), `check-inject-api.mjs` (policy, HTTP statuses on a throwaway server, a full stubbed `Run` over 24 steps). Never hit `/api/step` to test this.

## Hearts

Rare, fixed pickups that restore one life (built on the heart sprite and the testbed `hearts` option).
- **Spawn** (`src/hearts.js`, `spawnHearts`): one per `roomsPerHeart` (4) rooms, at least one, at most `maxHearts` (6; 0 = none), each in a different room, never on the start, portal, small prop or a coin. In a linear layout side rooms are filled first. Own PRNG stream (`seed ^ 0x2f6b1d57`), so dungeons, props, ghosts and coins never change (rule 8). Settings: Spawn group, `when: 'next'`. Enemies drop no hearts.
- **Pickup** (`Game.applyMove`): stepping on one while `health < maxHealth` takes it and heals one life (`healed`, a `heart` event); at full lives it stays on the floor. `heartPiles` is replaced, never spliced; `view().heart_cells` feeds the UI.
- **Respawn** (`Game.respawnHearts`, called by `applyMove` after `steps++` and before the pickup; a stay counts): a taken heart is queued in `game.heartsTaken` (`[{ cell, due }]`, `due = steps + HEART_RESPAWN` read at pickup; replaced, never spliced) and goes back into `heartPiles` on its own cell once `steps >= due`, except while the explorer stands on that cell (it waits until the explorer is elsewhere). `applyMove` returns `respawned` (count). Knob `world.hearts.respawn` (`heartRespawn`, default 200 steps, 0 = never, file-only, `live`; `HEART_RESPAWN` in dungeon.js via `configureWorld`). **The explorer is not told hearts respawn** (no rules sentence, memory field or move fact): it just sees the heart again through `seenHearts()` once that cell is lit. The `heart` event comes from `game.heartAt` (the step of the last pickup), not from a `heartPiles` count, so a same-step respawn cannot hide a pickup.
- **Explorer (fog-safe)**: `KnownWorld.seenHearts()` returns lit hearts only. Only while hurt does Jev hear of hearts: `surroundings.hearts` (nearest two, direction and distance), the move facts `Picks up a heart: restores a life.` / `Toward a seen heart (N steps after this).` and one `next_move` priority line. At full lives requests are byte-identical to before.
- **The `heal` approach** (perception.js `heartTarget`, `needsHeart`): offered in reviews only while a heart is reachable and the explorer is hurt. In the brain a quiet tick (no enemy in sight, no directive, not leaving, not in a tactic) switches to it by code, with no call: at half the lives or fewer for any reachable heart, above half for one within `HEAL_NEAR` = 12 known-path steps. It ends (back to `nearest_frontier`, no `plan.tried` row) when lives are full or no heart is reachable. A tactic parks it like any approach. Check: `scripts/check-hearts.mjs`.

## Regen (natural healing)

A hurt, living explorer heals `REGEN_AMOUNT` (0.5) lives every `REGEN_STEPS` (30) steps of `game.steps` (a stay counts), never above `maxHealth` (`Game.regenerate`, called from `applyMove`; dungeon.js `export let`s set by `configureWorld`). Knobs `explorer.regen.steps` (0 = off) / `explorer.regen.amount` (file-only, `live`). **Health can be fractional** (`1.5`): `damage` and hearts round to 2 decimals, a heart heals at most up to max (`healed` may be 0.5), the loss is still at exactly 0. `applyMove` returns `regen` (lives healed, 0 if none) and sets `game.regenAt`; `Run.playTurn` emits `{ id: 'explorer', type: 'regen', at, health }` (a `heart` event now fires only when a heart pile was taken). Jev reads only the fractional `self.lives`; no rules sentence mentions regen. The pane draws a half-filled heart. Check: `scripts/check-regen.mjs` (free).

## Victory

The portal is the only win on maps that have one; portal-less testbed arenas retain clearing. Outcomes are recorded in `game.winBy` (`'chest'` | `'cleared'`, `null` while playing) and sent as `view().won_by`:
- **`chest`**: `applyMove` onto the chest (unchanged).
- **`cleared`** (chest-less arenas only): `resolveAttack` (resolve.js), in the dispel branch, sets `won` and `winBy = 'cleared'` and emits `{ id: 'explorer', type: 'cleared', at }` when the dispelled ghost was the last one in `game.adversaries`. It fires **only on a dispel**, so an arena or dungeon that starts with no ghosts (`numAdversaries` 0, `maxAdversaries` 0) is never won at tick 0. The coin roll for that last ghost still happens first, but nobody can walk onto the drop once `won` is set (`applyMove` and `useSkill` are no-ops), so it is never collected. `stepAdversaries` returns at once, as for a chest win. The explorer's memory logs 'Cleared the portal-less arena.' (a win with `moved: false`; a chest win moves). The gameplay exception is restricted to portal-less testbeds; the explorer prompt states the portal objective. The UI shows 'Dungeon cleared'.
- **Portal only where a portal exists.** The user decided that on a map with a portal (every generated dungeon, and testbed arenas with a `treasure`) only stepping through the portal wins: `resolveAttack` sets the cleared win only when `game.dungeon.treasure` is `null`. Dispelling the last monster on such a map is just a dispel; the game goes on. Chest-less testbed gyms keep `cleared` so they stay winnable. `check-skills.mjs` section 11 covers both. Explorer rules, moods and encounter facts consistently describe reaching the portal as the win; fights remove obstacles and pursuers.
- Test hazard: in a chest-less arena any check that dispels the only ghost ends the game. Give it a spare ghost out of sight (`check-skills.mjs` sections 7 and 10, `check-dungeon.mjs` dispel test) unless a win is the point (`check-skills.mjs` section 11).

## Coins

The money system: coins lie around the dungeon from the start, and a dispelled ghost may drop one. A pile can lie on an unlit cell, so every explorer read is fog-guarded.
- **Opening coins** (`src/coins.js`, `spawnCoins(dungeon, { count })`): the same spread as `spawnAdversaries`. The count is `min(MAX_COINS, round(floorCells / FLOOR_PER_COIN))` (settings `maxCoins` 30, `floorPerCoin` 60, Spawn group, `when: 'next'`, through `configureCoins`; `maxCoins` 0 = none). Each room gets a shuffled list of free cells, the rooms are shuffled, and coins go round-robin. In a linear layout side rooms are favoured (they take two coins per round), so detours pay off. There is no distance rule, and coins never land on the start, the chest or a small prop, with one coin per cell. The stream is its own (`seed ^ 0x5be0cd19`), so dungeons, props and ghost spawns never change (rule 8, asserted over 20 seeds in `check-testbed.mjs` section 7). `newGame` puts them on `dungeon.coins` and the `Game` constructor copies them into `coinPiles`. Hidden state: explorer code never reads `.dungeon`. The file lives outside dungeon.js because dungeon.js may not gain a relative import.
- **State** (`Game`): `coinPiles` (`[[x, y]]`, one entry per coin, a repeated cell is a bigger pile), `coins` (the explorer's total), `coinRand` (the drop stream, `seed ^ 0x3c6ef372`, created on the first `coinRandom()`; never touches the dungeon or spawn `rng()` order, rule 8). `coinPiles` is **replaced, never spliced**, because `twin()` shares arrays.
- **Drop** (`resolveAttack`, dispel branch): every dispel rolls `game.coinRandom()` exactly once (even at chance 0 or 1, so the stream stays stable) and, below `coinDropChance` (Skills setting, default 0.6; every explorer text says only "may drop a coin", never the chance, and drops the clause at 0), adds a pile on the ghost's cell and emits `{ id, type: 'coin_drop', at }` after `dispelled`. The roll lives in resolve.js, not dungeon.js, because dungeon.js may not gain a relative import (check-props).
- **Pickup** (`applyMove`): stepping onto a cell takes every pile on it, `coins += n`, and the return carries `coins: n`. Ghosts never pick up, see or hear about coins (no `AdversaryView` change). Same-tick order: the explorer's strike drops the coin, then its step can take it. `Run.playTurn` emits `{ id: 'explorer', type: 'coin', at, gained, total }` when the total rose.
- **Explorer (fog-safe)**: `KnownWorld.seenCoins()` returns lit piles only. Jev gets: the objective in `rules()` (reach and step through the portal to win; dispel enemies to remove obstacles and pursuers, with coins held as the score, at 0 lives it loses them), "may drop a coin" in the combat sentence (no chance stated), `self.coins`, `surroundings.coins` (nearest seen piles) and the move fact `Picks up a coin.` / `Picks up N coins.`. Memory keeps `progress.coins`, a pickup event and `encounters.dispelled`. Whether a fight or a detour for coins is worth it is Jev's call, with help from P2's pull: the shared move fact `Toward N seen coins (K steps after this).` on each move that closes in on the nearest pile within 8 known-path steps (`COIN_NEAR`; no "away" fact, to save bytes), the `next_move` priority "Coins are the score: ..." while a pile is seen, the `collect_coins` approach, and a **coin decision**: when a pile is seen for the first time within 8 steps (at least `COIN_EVERY` = 10 steps after the last one, no tactic, not leaving; a review or `leave_now` tick delays it) the tick's request gets a `next_approach` Choice and a pick other than the current approach at >= 0.5 switches at once. Since P4 it is asked only on a decision tick: the `coins` mood trigger asks the mood first (one sentiment call), or another trigger's call that tick serves (see Triggers); `check-dungeon.mjs` sections 4h and 4i cover it. In stubbed 21x21 coin gyms (10 seeds, 60 ticks) most coin decisions ride on another trigger's call: about 0.2 extra sentiment calls per game, and as many coin decisions as before.
- **UI**: `view().coin_piles` / `view().coins`; a Coins stat next to Lives, a coin sprite (`sprites.js` `coin`) as a Pass B entity on lit cells (Reveal shows unlit ones), gold minimap dots, log lines for `coin_drop` and `coin`.
- **Checks**: `check-skills.mjs` section 10 (drop at chance 1 and 0, stacked piles, determinism, twin safety, `publicView`, a dark pile absent from `seenCoins()` with a byte-identical request, the move facts).

## Explorer brain, memory & Jev client

**`src/jev.js`:**
- `askJev(state, questions, body?)` POSTs `{ model: 'jev-latest', state, questions }` (or the pre-built `body`) with a Bearer key and returns `answers`.
- Each request is **hedged**: copy 0 goes at once, copy 1 only if nothing has answered after `HEDGE_DELAY_MS` = 800 ms; the first answer wins and the other is aborted. A normal call is one request (measured: about 250 ms; the 1-4 s tail is what the second copy covers).
- Each copy retries up to `RETRIES = 3` times on 429, 529 or network errors, with a 20 s timeout per attempt.
- One logical call can therefore bill several times.

**What Jev reads (explorer).** `state = { game, self, surroundings, threats, plan, recent }`, built by `ExplorerBrain.#state` from memory plus `situation()` (the old `{ game, memory, situation }` shape, `situation.threats`/`situation.treasure` and the verbatim memory are gone):
- `game`: `rules()`, one sentence block (objective with coins folded in, speed from `speedPhrase`, lives, grace, what `threats.visible` / `threats.remembered` mean, and, with an attack skill, what the sword does: always hits an adjacent adversary, `damage` hp, knockback and `stunTicks` stun, gone at 0 hp, "may drop a coin" (left out at `coinDropChance` 0, the chance never stated); `combatRule` also says the stun means the next strike lands before it can claw (only claimed with `stunTicks` >= 2 and the sword's cooldown below `stunTicks`), that an adversary's claw needs `clawCooldown` steps to recharge and that the shield stops it `shieldChance` of the time (only with a block skill); numbers from the live skill and `skillConfig()`).
- `self`: `{ lives, max_lives, hit_protection_steps, coins, skills, mind: { id, since_step, recent } }`; `mind.recent` is the last 5 picks as runs, e.g. `"steady×3 → wary"`.
- `surroundings`: from `situation` (above), plus `moves` on a decision tick with tactic questions (the shared move facts, one sentence per direction).
- `threats`: `{ visible, remembered, encounter }`. On the request that carries the `tactic` question, `encounter` drops `slip_past`, `hide`, `run_away` and `exit` (`TACTIC_FACT_KEYS`): each feasible tactic's option already states them.
- `plan`: `{ approach { id, current, since_step, interrupted | null }, tried[{ id, steps, reason }] }` (`tried` is left out of the request with the `tactic` question). A coin switch and the hand-back from `collect_coins` write no `tried` row (`changeApproach` in memory.js): they are not failures.
- `recent`: `{ path (compass words), back_and_forth, revealed_since_approach, steps_since_approach, revisits_last_10, encounters, events }`.

**`ExplorerBrain.takeTurn()`** (brain.js). `new ExplorerBrain(world, { ask, memoryDir })` builds the initial memory (it runs `approachTarget`, so the world must be ready). Review info, encounter bookkeeping, the tactic goal, the remembered sightings and the last request bodies are `#private` fields, so there is one brain per `Run` and no module-level mutable state in `explorer/*`. Each tick starts with `#observe()`, which updates the sightings (below).
- **Ordinary tick:** with exactly one legal move, the move is **forced** and no Jev call is made. Otherwise it makes **one** request with a `next_move` question (plus an approach review every few steps).
  - Option order is shuffled every tick, because Jev leans toward the first option.
  - An illegal choice falls back to `legal[0]`.
- **Decision tick** (an approach decision). It makes one extra request, **first and in sequence**:
  1. `sentiment` (Choice). It sees the state and the sentiment-free `threats.encounter`. Each option states the circumstances that call for it (`when`), its effect (min gap, end ticks, note), and, while an adversary is in sight, which tactics its `min_gap` leaves open here.
  2. The normal tick request, with the new sentiment already in `self.mind`. While an adversary is in sight it adds `tactic` (Choice over the feasible tactics only) plus a **speculative** `move_if_<tactic>` per option, each judged on that tactic's move facts (`stay` is just "Stand still." there; its full fact is in `surroundings.moves`). The move taken is the answer for the chosen tactic, so the move on the decision tick already follows it. With one feasible tactic, code takes it and asks no Choice.
- **Merged triggers.** A pending decision (`start`, `exit`, `review`, `dispelled`) and an `encounter` on the same tick cost **one** sentiment call: the encounter trigger wins and the pending one is dropped. A trigger without an adversary in sight waits through forced ticks.
- **Triggers:**
  - `start`: the first tick.
  - `encounter`: an adversary is in sight with no tactic on (after `REDECIDE_COOLDOWN` ticks since the last decision), an id not seen in this encounter appears, or a visible one goes patrol→chase.
  - `tactic_failed`: the tactic's target is gone, or (except for `run_away` and `engage`) the gap fell below `min_gap`, or the explorer is **going back and forth** (`PINGPONG_FAILS = 3` moves since the last decision that returned to the cell just left, `recent.back_and_forth`). A ping-pong also fills the brain's `#exclude` with the two bounce cells and the old target (with the tabu move level on the two cells go into the tabu list as encounter-long `cell` entries instead, and into the private `#bounceCells`; `#excluded()` = `#exclude` plus those, and is what every target function receives), so `tacticFeasibility` and `approachTarget` pick something else on the re-decision; it is cleared when an encounter starts and when it ends. At most once every `REDECIDE_COOLDOWN = 3` ticks.
  - `chase_over`: nothing in sight for the sentiment's `end_ticks`. The parked approach resumes.
  - `hit`: a life was lost while a tactic was on (`noteHit` sets it pending for the next tick), so Jev can rethink a fight (`engage` never fails by gap on its own).
  - `exit`: the portal was first seen (the brain records it once: event, `exit` landmark). It also queues the `leave_now` question for the next tick with a real choice and no tactic question. At step 0 (a lit testbed arena) it replaces the pending `start`, so it is still one sentiment call.
  - `review`: a review switched the approach. The sentiment is asked on the next tick, so it is only paid for when the approach really changed.
  - `coins` (P4): a pile was first seen within 8 known-path steps (the coin-decision detection, `#coinDue`), with no tactic, not leaving, no review due and no adversary in sight, at least `REDECIDE_COOLDOWN` ticks after the last decision and `COIN_EVERY` = 10 steps after the last coin decision. It asks the mood, then the `next_approach` coin question in the same tick. When another trigger is due that tick (and no tactic question), that trigger's single sentiment call serves and the coin question follows it; without a decision tick the coin question is not asked (it waits).
  - `dispelled` (P4): the tick after the explorer dispels an adversary (`#useSkill` sets it pending unless something else is). The same merge rule applies (a `chase_over` on that tick takes it).
- **Remembered sightings (rule 1).** `#seen` maps adversary id → `{ id, cell, step, chasing, hp, maxHp, level, clawDamage }`, written only from `world.visibleAdversaries()` and never updated while the adversary is out of sight. A sighting is dropped when older than `REMEMBER_STEPS = 30` steps or when the explorer is within `SIGHT_RANGE` of the frozen cell with `knownLineOfSight` to it while that id is not visible. The ones not in sight become `threats.remembered`, per-move "where an adversary was last seen" facts, and (within 15 steps) an avoid zone for exploration targets (`avoidZone`).
- **Known-path progress and retreat redirect (DUNGEON_DIRECTION_PLAN section 4, fog-safe).** The brain keeps, as `#private` fields (never in `memory.json`, memory shape unchanged), `entryDistance` (known-floor path length from the explorer's own start cell to where it stands; a BFS rebuilt only when the known map changed) and `furthestEntry` (its maximum). It reads no hidden map, room order or spine (`src/route.js` is for the spectator HUD and must never be imported by explorer code). The pure rules and constants (`RETREAT_WINDOW = 8`, `RETREAT_CELLS = 6`, `RETREAT_REVISITS = 6`, `RETREAT_COOLDOWN = 20`, `FORWARD_SLACK = 4`) live in `progress.js`. A **retreat** is entryDistance down by >= 6 over 8 ticks, on visited ground for >= 6 of them, while nothing asks for it: an exploration approach (`nearest_frontier`, `largest_unexplored`, `far_side`), no directive, encounter, pending decision, coin question, portal run, adversary in sight or sighting younger than 15 steps, and no reachable heart while hurt. While any of that holds the window is cleared, so a detour or a fight never counts as retreat afterwards. When it fires, the exploration goal (`#approachGoal`, which `approachTarget`'s frontier branch keeps, so Jev's move options follow it) is set to the nearest reachable frontier whose entryDistance is within 4 of the **deepest reachable frontier's** (judged against the frontier set, not `furthestEntry`: a deep explored dead-end side room would otherwise push "forward" past every real edge and leave only edges near the entry; `furthestEntry` is informational). When everything ahead is explored the only edges are behind and that is the goal. Walking toward the committed goal (known-path steps to it falling across the window) is never flagged; walking away from it is. Cooldown 20 steps. `ExplorerBrain` / `Run` take `progress: false` as a measurement arm (tracks, never redirects); `scripts/measure-progress.mjs` prints the on/off table against the route ground truth. No forced move and no new request text: only the target Jev's options describe changes. A finished coin or heart detour resumes the forward edge the same way, but only when it differs from the plain nearest one. `brain.progress` is a read-only view for the checks; `check-progress.mjs` covers it.
- **Minds** (`SENTIMENTS` in brain.js, read from `memory.sentiment.id` every tick). Each has `min_gap`, `end_ticks`, `priority` (a line in `next_move` and the `tactic` question), `move_priority` (the same rule, short, for the speculative `move_if_<tactic>` questions), `when` (what Jev reads when picking it), `note` and `skill_priority` (its stance on striking, in the `skill` question and in `next_move` while a skill is offered: every mood strikes an adjacent adversary whenever the sword is ready, since the stun is also the best defence (checked in check-skills section 12); the moods differ on blocking and on walking toward a fight: `bold` also steps up to a hurt one and engages adversaries it can beat). Each changes behaviour in code: `min_gap` drives tactic feasibility and targets, the gap warning in move facts and `tactic_failed`; `end_ticks` ends the encounter.

  There are exactly four (P4; they replaced scared, risk_averse, cautious, curious, courageous and aggressive, and memory validation accepts only these ids, `MOOD_IDS` in memory.js). The sentiment question asks which stance best helps advance to the portal. Moods describe how to pursue that goal: wary minimizes exposure; cautious regroups for renewed advance; bold takes favourable fights; fearless hunts enemies for glory. No mood treats clearing as the game win.

  | id | min_gap | end_ticks | goes after |
  | --- | --- | --- | --- |
  | wary | 4 | 5 | getting away: run, hide, the portal only if leaving is already worth it. `when`: outnumbered, a chaser within 3 steps with no route past, or 1 life left |
  | steady (default before the first pick) | 3 | 4 | the plan: explore, coins on the way. `when` (P6): no adversary in sight and nothing else clearly fits (a plan to follow, no coins, little left nearby), or exactly one in sight and fighting it is clearly bad (sword not ready, or not full lives and no hit protection); never with 2+ known (wary). It no longer claims a ghost that has just come into sight at range, which was the P5 bottleneck |
  | greedy | 3 | 2 | loot: coins and unexplored rooms, detours fine. `when`: coins in sight or plenty unexplored, no adversary in sight, full lives or hit protection |
  | bold | 2 | 1 | the fight: engage lone or weak adversaries. `when` (P6): a lone adversary is the only one known (in sight at any distance, or remembered), the sword ready (`self.skills`), full lives or hit protection; no distance cap |
- `next_move` priorities (ordinary tick):
  1. Once the portal is seen: with `go_to_exit` or `race_to_exit` as the approach, "Take a move onto the portal; else move closer to it along the known path."; otherwise "A move onto the portal ends the game: take it only if leaving now is the plan or an adversary would otherwise strike you."
  2. Only while threats are visible: never step into one, avoid moves below `min_gap`, plus the current tactic's move hint (e.g. `run_away` keeps the distance growing; `slip_past` may move toward it while the gap holds).
  3. Do not head toward where an adversary was last seen (only when `threats.remembered` is non-empty).
  4. The sentiment's priority line.
  5. Avoid `stay`, follow the approach, reveal new cells, avoid backtracking.
  The speculative questions keep only the portal line (if the portal is seen, shortened), the safety line and the mind's `move_priority`.
- Approach reviews:
  - They run every `REVIEW_EVERY = 8` steps, and only once 8 steps have passed on the current approach.
  - They are skipped during `go_to_exit` and any tactic.
  - Seeing the portal immediately commits to `go_to_exit`, including the approach parked under a tactic. Player directives keep their priority. No later review or coin choice overrides the portal plan. Legacy **`leave_now`** remains a compatibility fallback, not the gate to the goal.
  - A review adds `approach_working` (Noul) and `next_approach` (Choice over exploration approaches) **to the same request**.
  - The approach switches only if `approach_working < APPROACH_FAILING (0.5)`.
- Code policies:
  - Seeing the portal changes no approach. Only a `leave_now` above 0.5 switches to `go_to_exit` (mid-encounter it replaces the parked approach instead). Neither writes a `plan.tried` row (`changeApproach`; `replaceInterrupted` drops the parked one without a row), and both return `policy: { from, to: 'go_to_exit', reason }` on the turn (`from` is the parked approach mid-encounter).
  - Tactics park the exploration approach with `interruptApproach`. Switching from one tactic to another keeps the parked approach. **Tactics never go into `tried`.**
- **Turn shape:** `{ step, dir, forced, revealed, won, move_decision, held, decision, review, policy, apiMs, tabu }`. `held` is true on an engage hold tick (below). `tabu` is null with `explorer.tabu.enabled` off, else `{ tactic?: [...], mood?: [{ attr, steps_left | 'encounter', reason }], removed, lifted, removed_moods, lifted_moods }` (`removed` / `lifted` are tactic ids, the `_moods` pair the mood ids; see [Tabu](#tabu-plan-tabu)).
  - `move_decision` = `{ choice, probabilities, confidence, options } | null`.
  - (C3, toggle on only) the gap every mood keeps is `effectiveProfile(memory, C).min_gap` (delta +2 below C 30, +1 below 40, 0 to 79, -1 from 80, never below 2), `engage` needs C >= 40, `self.confidence` is `'<value> <band>'` on every request, one explaining sentence sits in the sentiment question only, and the UI shows a meter from `turn.confidence`. Toggle off: nothing changes (request-hash baseline).
  - `confidence` = `{ value, band, delta, reason, capability, history, tier, panic }`: C after the turn (capability + history), its band word, the change since the previous report (a hit or block that `Run.playTurn` forwards after a turn shows up in the next turn's report), the events behind it (`regen` alone is not named), the two terms, the tier (`low` <= 35, `mid` 36..75, `high` > 75, with 5 points of hysteresis) and whether the explorer is in `panic`.
  - `decision` = `null | { trigger, sentiment: { choice, probabilities }, tactic: { choice, probabilities, options } | null, apiMs }`.
  - `apiMs` covers both requests.
- **Engage hold (PLAN-motivation P7a).** With approach `engage`, exactly one adversary in sight, hunting (`chase`) and not stunned by the explorer's own strike, the sword ready, and the explorer standing on the engage target (the holding cell 2 known-path steps off, or already next to it), `#holding()` makes the move `stay` in code: no `next_move` / `move_if_*` question, so a hold tick often costs no call (the `skill` question still goes out whenever the sword has an option, so the strike lands the tick after the ghost steps adjacent). The tactic choice stays Jev's; the hold is execution. Released (the normal question is asked, and the usual `tactic_failed` machinery may re-decide) after `HOLD_MAX = 5` consecutive hold ticks without the ghost coming, or after `HOLD_ADJACENT_MAX = 2` ticks beside it without a strike. Not held: a stunned ghost (close in), a patrolling one, a second adversary in sight, no ready sword, a decision tick that asks the tactic question (its `move_if_engage` answer moves; it also restarts the hold count). The hold is deliberately **not** gated by `#loneFight` (lives, `fight.steady`, at most 2 strikes): it makes no claim (the stakes sentence and the claw clause stay gated), and a gated hold measured worse in the review's duels (walk-in over the 24 placements: ghost hp 3 gave 4 claws, `stunTicks` 1 gave 24-27, 1 life lost 4 of 24 games, against 0, 0-1 and 0 with the hold). The reason, measured: in 3 of 8 live fights the explorer stepped off the holding cell and was clawed first. Reported as `turn.held`. `new ExplorerBrain(world, { hold })` / `Run` opts `hold` (default true; false only in `check-duels.mjs`, to show what the hold buys; `'multi'`, PLAN-confidence-mood phase 2: with 2 or 3 adversaries in sight it holds when the nearest hunting, unstunned one (`holdGhost` in encounter.js, ties by id) is at gap 2 or adjacent and the explorer is on the engage target with the sword ready; 4 or more in sight never hold; the releases and `engageTarget` are unchanged; the stay fact reads "Holds this cell, 2 steps from the nearest: ..." with several in sight, today's text for one; with `true` requests are byte-identical to before). Over the 24 placements (`check-duels.mjs`): hold on = 0 claws (ghost hp 1, 2, 3), hold off + walk-in = 4 claws in 4 placements. Engage move text (P7a-A): under `engage` a step that ends next to a hunting, unstunned ghost says "Steps next to it: it can claw before you strike." (the ghost's id with two in sight); `stay` on the holding cell reads "Holds this cell, 2 steps from it: it steps next to you and you can strike first."; the engage move questions carry no mood priority line (so no "moving toward an adversary is fine") and the ordinary-tick engage priorities drop "Stay makes no progress ...", "Follow the approach", "reveal new cells", "avoid backtracking" and the coin line. `explorer/brain.js` now also imports `threatDistance`, `threatsOf` from `./encounter.js` (a sibling file: the static guard's allowlist is unchanged).
- **Request helpers:** `brain.lastRequest()` returns the latest request; `brain.lastRequests()` returns both requests of a decision tick. The injected `ask` is called as `ask({ kind: 'sentiment' | 'tick', state, questions, body })`. `noteCaught(adversaryId)` and `noteHit(adversaryId)` are methods too.
- `rules()` derives "about 3 steps for every 5 of the explorer's" from `ADVERSARY_SPEED` (`speedPhrase`), and lives and grace from `EXPLORER_LIVES` / `GRACE_TICKS`, so it follows the settings.
- **Cost:** a decision tick costs 2 requests instead of 1. Each encounter costs about 2 decision ticks (`encounter` and `chase_over`), plus `tactic_failed` re-decisions (≤ 1 per 3 ticks). On top of that come one `start` decision per game and one per portal sighting, review switch, dispel and, at most every 10 steps, newly seen nearby coins (P4's `coins` and `dispelled` triggers: each one extra sentiment call outside danger, merged into the encounter's call when they coincide).
- **Encounter framing (P6).** On an `encounter`, `tactic_failed` or `hit` sentiment request the question gets one more sentence (`#stakes`): "A lone adversary you can strike first costs at most one claw and a dispel removes it for good; running may leave it hunting you." Only for a `#loneFight`: one adversary visible and none remembered, the sword ready, `stunHolds` (stun >= 2 and above the sword's cooldown, the `fight.steady` gate of engage's fact: check-skills section 12 measures at most one claw for 24 ghost placements), at most 2 strikes to dispel it (from the visible hp), and lives above `clawDamage` with full lives or hit protection (one claw cannot end the game). Absent with two ghosts, a remembered one, `stunTicks` 1, no sword, 1 life, a 3-strike ghost or nothing in sight (about +180 B on that request). On the `tactic` question, under `steady` or `greedy` with `engage` offered and the same `#loneFight` gate, the first priority is "Default: engage a lone adversary while the sword is ready (you act first). Run away when cramped or without the sword." and the old engage line (with "outnumbered") is not sent; in every other case the priorities are unchanged. Checks: check-dungeon section 4i (P6 block).
- **Request size.** The largest explorer decision tick is about 9-10 KB (every tactic feasible incl. `slip_past` and `race_to_exit`, lit coins, a remembered ghost: about 9.2 / 9.8 KB after P3; `leave_now`, the coin decision and `plan.tried` are never on a tactic request). `check-dungeon.mjs` asserts ≤ 9500 bytes for a chasing adversary (5 tactics) and ≤ 10500 for a patrolling one (6 tactics). Adding a state field or a longer option means re-checking these bounds; `measure-memory.mjs` prints the sizes per fixture arena.

**`memory.js`:**
- Shape: `{ approach { id, current, thought, since_step, tried[], interrupted }, progress { steps, known_floor_cells, revealed_since_approach, steps_since_approach, revisits_last_10, coins }, sentiment { id, since_step }, sentiment_history[{ id, step }], recent { moves[], cells[], back_and_forth }, encounters { count, escaped, hits, dispelled, last_at_step }, events[{ step, text }], landmarks[{ kind, cell, step, note }] }`. Gone: `objective`, `findings`, `latest_action`, `danger`, `sentiment.profile_note` (the profile text now comes from `SENTIMENTS`).
- `approach.thought` is ≤ 60 chars and set for every approach. On resume it is looked up by id.
- `sentiment.since_step` moves only when the mood changes. `sentiment_history` keeps the last 5 picks.
- `recent`: the last 6 moves and 8 cells; `back_and_forth` counts moves that returned to the cell two positions back (standing still never counts).
- `encounters`: `count` (an encounter began), `escaped` (it ended unhurt at `chase_over`), `hits` (`noteHit` / `noteCaught`).
- `events`: short milestones, newest 6 (saw the portal, dropped an approach after a review, hit, caught, won ("Stepped through the portal with N coins." or the cleared line), struck `a1` (hp left), dispelled `a1` (and whether it dropped a coin), picked up coins (with the total)). The step is its own field, never repeated in the text.
- `landmarks`: located facts, kinds `exit`, `dead_end_explored`, `hit_here`, `hiding_spot_used`; one per kind + cell, at most 8, oldest non-exit evicted first (the portal landmark is never evicted). Perception turns them into direction/distance each tick.
- `saveMemory` validates the shape (and throws if it's wrong), then writes `memory.json` (the source of truth, but **not** sent verbatim: `ExplorerBrain.#state` picks from it) and `memory.md` (rendering only, never read back).
- It runs at the end of every `takeTurn` and in `noteCaught` / `noteHit`.
- **Any new memory field that reaches Jev must be fog-safe** and fit the validation limits (`LIMITS` in memory.js): approach text 240, tried 5, thought 60, sentiment_history 5, events 6 (text 200), landmarks 8 (note 120), recent moves 6 / cells 8.
- The revisit window lives in a WeakMap keyed by the memory object (the one remaining WeakMap), so it never reaches Jev or disk. The brain's encounter bookkeeping, tactic goal and remembered sightings are private fields of `ExplorerBrain`, so sightings are **not** in `memory.json`. `memory` itself stays a plain object, never a class instance.

## Route (spectator navigation)

`src/route.js` gives the browser a sense of where the explorer is on the way to the portal. **It is built from hidden data (tiles, treasure), so it is spectator-only: `Run.view().route` and nothing else.** No explorer file may import it, no Jev request may carry any of it (`check-request-hashes.mjs` and the static fog guard in `check-dungeon.mjs` are the proof), and it adds no `rng()` call: it is derived after generation from the finished tiles, so layouts stay byte-identical.

- `buildRoute(dungeon)` -> `null` without a treasure (testbed), else a frozen route: `spine` (shortest 4-connected path start to portal), `waypoints` (its corners, for the debug overlay), `length` = `spine.length - 1`, and flat per-cell arrays `attach` (spine index of the nearest spine cell **by walking distance**, ties to the lowest index), `offset` (walking cells off the spine) and `toPortal`. Walking distance is the point: two corridors either side of a wall never swap progress, and a side room keeps its junction's progress with offset above zero.
- `RouteTracker.update(game, { events })` runs once per tick at the end of `Run.#playTurn` (and once in the constructor); `snapshot()` is `view().route` (shape in CONTRACT.md). State from the last 8 samples: `exploring` when more than 3 cells off the spine; net >= +3 `advancing`; net <= -5 `backtracking` (kept until net >= +2); otherwise `stationary`. A window that is not a 4-neighbour step resets.
- The cue (`Heading toward the entrance — portal is the other way.`) shows when backtracking and at least 6 cells behind the furthest point, once per retreat (re-armed only by advancing), at least 25 ticks apart, and clears when the state leaves backtracking. `suppressed` says why it is held back: `combat` (a chasing ghost that sees the explorer, or a hit / bump / strike / blocked event within 3 ticks), `portal_known` (the portal cell is lit), `over`, or `detour` (the explorer's approach is `heal` / `collect_coins`, or a player directive is active; `Run` passes `memory.approach.id` and `directive` to `update`, one-way: nothing flows back). Priority: over > portal_known > combat > detour. A suppressed cue does not use up the once-per-retreat cue.
- Constants (`WINDOW_TICKS`, `DEADBAND_CELLS`, `DETOUR_OFFSET`, `BACKTRACK_ENTER`, `CUE_BEHIND`, `CUE_COOLDOWN`, `LOOKAHEAD`, ...) sit at the top of the module on purpose: they are not config-registry knobs.

## Testbed (small test arenas)

`src/testbed.js` builds a tiny arena instead of a generated dungeon, so explorer reactions (to adversaries, cover, corridors, open space) can be watched in isolation. `buildArena(config)` returns `{ dungeon, adversaries, config }` (the adversaries are `Adversary` instances); `turn.js` `newTestGame(config, opts)` wraps it in a `Run` through the same constructor as `newGame`, so both start from identical state. It costs no Jev calls.

**Config** (all optional; JSON values or URL-query strings, coerced and validated by `normalizeConfig`):

| Key | Default | Meaning / validation |
| --- | --- | --- |
| `size` | `[11, 11]` | Interior floor `[w, h]`, `"WxH"` or one number; each side 3..60. The map is `(w+2)×(h+2)` with a wall ring, so floor is x 1..w, y 1..h. |
| `seed` | `1` | Drives prop and adversary placement and the patrol RNG. Same config → same arena. |
| `start` | `'center'` | `[x, y]` / `"x,y"` (wall ring included in coordinates) or `'center'`. Must be inside floor. |
| `treasure` | `null` | `null`/`'none'` (no chest: the game only ends when caught), `'far'` (a floor cell farthest from the start by path), or `[x, y]`. Must be reachable. |
| `numAdversaries` | `1` | 0..8, placed at random on floor at least `minAdversaryGap` steps (path) from the start, never on the chest. |
| `adversaries` | `null` | Explicit cells `[[x, y], …]` (URL: `"x,y;x,y"`); overrides `numAdversaries`. |
| `minAdversaryGap` | `4` | Minimum path distance for random adversaries (≥ 1). |
| `adversariesInSight` | `null` | `true`/`false` restricts random adversaries to cells the start can / can't see (`SIGHT_RANGE` + LOS). `null` = either. |
| `kinds` | `'ghost'` | The monsters' kind: `'ghost'`, `'troll'`, `'tree_giant'`, `'wolf'`, `'mixed'` (the spawn draw at 0.5, seeded by `seed`) or a list (URL: `troll;ghost`) applied per monster in id order and cycled. A bad id or an empty list throws `TestbedError`. Trolls hunt like ghosts but are slower, tougher and hit harder (see Kinds). |
| `levels` | `2` | The monsters' level (not the character trait levels): `'random'` (`assignLevels`, seeded by `seed`: ghost 1-2, troll 2-3), a number 1-4, or a list (URL: `1;3`) applied per monster in id order and cycled. A bad value or an empty list throws `TestbedError`. 2 is today's stats; tree giants always use level 4 and wolves level 2, including explicit overrides; with `monsters.levels.enabled` false other kinds use level 2. See Enemy levels. |
| `characters` | `'standard'` | The ghosts' characters: `'standard'` (all), `'mixed'` (the shuffled preset deck of `assignCharacters`, seeded by `seed`), one preset id, or a list (URL: `ambusher;timid`) applied per ghost in id order and cycled. Preset ids are in `character.js`; a bad id or an empty list throws `TestbedError`. Independent of the `adversaryCharacters` setting, which only affects generated dungeons; the default leaves every existing arena unchanged. |
| `props` | `'none'` | `'none'`, `'few'`, `'many'` (random 1-3 cell solid clusters plus small props; never next to the start or chest, never cutting floor off), or an explicit list `[{ kind, x, y, flip? }]` of `SOLID_KINDS`/`SMALL_KINDS`. **`forge` is a footprint kind**: `{ kind: 'forge', x, y, w?, h?, flip? }` where `x, y` is the footprint's top-left cell (min x, min y), `w` by `h` is 2x2 (default), 2x3 or 3x2 (`FORGE_SHAPES`); every cell must be inside floor and not the start, and becomes a solid prop cell (`props` gets one entry per cell: the anchor carries `w, h`, the others `part: true`). | `map` | `null` | ASCII rows (array, or one string split by newlines or `/`) overriding `size`, `start` and the shape: `#` wall, `.` floor, `@` start (required), `T` chest, `A` adversary, `p` solid prop, `s` small prop, `c` coin. | `ghostSkills` | `'default'` | `'default'` (claw strike) or `'none'` (harmless ghosts, for exploring tests); `ghostSkillSetOf(config)` gives the `buildSkillSet` argument. |
| `ghostHp` | `null` | 1..5 hit points per ghost; `null` = the Skills setting `ghostHp`. |
| `coins` | `0` | Coins lying around at the start: a count 0..60 (spread by `spawnCoins` on its own stream, so the arena is unchanged) or explicit cells `[[x, y], …]` (URL: `"x,y;x,y"`; not wall, not the start). ASCII `c` cells override it. Independent of the `maxCoins` / `floorPerCoin` settings. |
| `morale` | `null` | Starting morale 0..100 for every monster (and the baseline it returns to; see [Monster morale](#monster-morale-plan-monster-morale)). `null` = each monster's character decides. It only acts with the `monsterMorale` toggle on, and never changes the arena. |
| `hearts` | `null` | Floating hearts at explicit cells `[[x, y], …]` (URL: `"x,y;x,y"`; inside floor, at most 60). Unknown keys, bad values and impossible placements throw `TestbedError` with a readable message (the server answers **400**).

**How a testbed arena differs from a dungeon** (expect these when reading results):
- Arenas up to 9×9 with a centred start are **fully lit at step 0** (`LIGHT_RADIUS = 7`), and the default 11×11 leaves only its corners dark: little or no frontier, nothing to explore, and a placed chest is usually seen at once, so the explorer goes straight to `go_to_exit`. To test reactions to adversaries, leave `treasure` out, or hide the chest out of light with a `map` (e.g. at the end of a corridor longer than 7).
- `rooms` is one room over the whole inside, so patrols wander the whole arena. `decor` is always empty. `dungeon.testbed` is `true`, and `view` sends `testbed: true`.
- Adversaries are built with `new Adversary({ id, pos })` (the contracted shape) and start in `patrol`; they do not go through `spawnAdversaries` (its 20-step / out-of-sight rule can't hold in a small room).
- `generateDungeon` and its `rng()` order are untouched; the testbed uses its own stream (`seed ^ 0x51ed27a3`).

**Adding an option:** add it to `DEFAULTS`, parse and validate it in `normalizeConfig` (accept URL strings too), apply it in `buildArena`, cover it in `check-testbed.mjs`, and add a row to the table above.

## Server & UI

**Route HUD** (`public/app.js`, "route guidance"; spectator only, never steers): reads `view.route` (null/absent on an old server or a portal-less arena, and then everything below is simply not drawn). A pixel chevron in the knight's amber trail colour (`#ffd98c`, `#0a1126` edge) floats beside the knight toward `route.next_waypoint` (iso-projected, 2-frame bob); it is hidden when `suppressed` is `portal_known` / `over` (the portal's own visual wins) and stays while backtracking. A "Route" stat in the HUD grid shows a progress bar (`progress`), a tick for `furthest` and the `state` word (red fill while backtracking). `route.cue` shows as a non-blocking toast at the top of the board: it fades in, stays while non-null, fades out when it clears, and is appended once to the Danger event log per continuous non-null run (never re-popped across frames). The **Route (debug)** checkbox next to Reveal map draws `route.waypoints` as a cyan (`PALETTE.brain`) polyline on the board and the minimap; the spine is hidden map, so it is never drawn without it. Like Reveal it is not persisted.

**Server** (`server.js`):
- Routes:
  - `GET /`, `/app.js`, `/settings` (settings.html; the pages use relative URLs so they work under a hub prefix: keep new `fetch`/`src`/`href` paths relative), `/style.css`, `/sprites.js`, `/props/*.js` (the `STATIC` whitelist).
  - `GET /api/settings` → `settings.view()` (`{ schema, values, defaults, pending }`); `POST /api/settings` with `{ values }` validates, saves `settings-<port>.json` and applies the live knobs at once (400 with the reason on a bad value). Knobs marked `next` (spawn density, lives, light radius, map size, room area) apply from the next `POST /api/new` (`settings.applyNextGame()`). The schema lives in `src/settings.js`: to add a tunable, add a `SCHEMA` row and wire it through `configureWorld` / `configureAdversaries`.
  - `GET /api/state` → `{ game: run.view()|null, memory: run.memory|null }`.
  - `POST /api/new` → `{ game, memory }`. It waits for any in-flight step. An optional body `{ seed: <integer> }` replays that normal dungeon (the P6 measurement uses it); `{ testbed: {...} }` builds a [testbed arena](#testbed-small-test-arenas) instead; a bad config returns **400** with the reason, a non-JSON body 400.
  - `POST /api/step` → `{ game, memory, turn }`. Returns **409** for no game, game over, or a step already running, and 502 if the turn throws.
- `.env` is loaded *before* the dynamic `import('./src/turn.js')`. Keep that order. `settings.js` is loaded (`loadSettings`) at startup, before the first game.
- The pane's memory display reads explorer memory (UI pane: events / encounters / landmarks / recent, plus the approach thought and mind); the UI agent owns its details.

**Step loop** (`public/app.js`):
- `init` never auto-starts, so a page load costs nothing. With `?testbed…` in the URL, `init` and Reload always `POST /api/new` with the query as the testbed config (so the page shows that arena, not the server's current game).
- The chest may be absent (`game.treasure === null`) in a testbed arena; the renderer and minimap skip it.
- One `loop()` runs at a time. `epoch` is captured per request and bumped by Reload, and stale answers are dropped.
- A 409 on a finished game ends the loop quietly. Any other failure pauses with a message.

**Isometric renderer** (v3 look):
- Projection:
  - `TW = 32`, `TH = 16` art px.
  - `isoX = (x - y)·16`, `isoY = (x + y)·8`, measured at the cell centre (x+.5, y+.5).
  - Walls are 1 or 2 blocks tall (`WALL_H = 11` px per block, `MAX_BLOCKS = 2`; 25% of walls are 2 blocks, `TALL_WALL_SHARE`): a lit top, a medium left face and a darker right face, shaded per block. Height is `hash(x, y, seed ^ 0x5a17) < 0.25 ? 2 : 1`, computed in `app.js` (`indexHeights`) from the cell and `game.seed` only: no rng() draw, no server or `publicView` field, no gameplay effect. Floors stay flat (z = 0). A wall face is hidden only by a shown wall in front that is at least as tall; wall decor sits on the lowest visible block. Culling pads `dMax` for `MAX_BLOCKS` of height.
  - Big decor (`fireplace`, `arch`, `gate`, `banner`) is 1 or 2 blocks tall: `blocks = 1 + floor(hash(x, y, seed ^ 0x7b19) * 2)` in `indexProps`, no rng() draw. The 2-block art is the 1-block grid with its `stretch` row (in `wall-art.js`) repeated `WALL_H` times (`wallTall`/`metaTall` from `buildProps`). Clamped: a 2-tall item on a face with fewer than 2 visible blocks (`nb - hn < 2`) draws as 1-tall, so with 2-block walls a tall item only shows on a 2-block wall with no wall in front. Visual only.
- Pixel look:
  - Everything draws into a low-res offscreen buffer, blitted at integer scale `S` with smoothing off.
  - `resizeBoard` must re-set `imageSmoothingEnabled`, because every resize resets it.
  - The camera snaps to whole art pixels.
- Depth:
  - Pass A draws the flats: floors, fog glow, trail.
  - Pass B walks the diagonals `d = x + y`, drawing walls and then the entities at that depth.
  - While an entity moves, its depth is the larger of the from and to cells. Ties draw chest, then ghost, then knight.
- Culling is by diagonal (`d = x + y`, `e = x - y`), padded for wall and sprite height.
- Tiles are pre-rendered once into caches (`floors[band][variant]`, `walls[band][cap][mask]`, `fogTiles`), so each frame is only `drawImage` calls.
- Palette:
  - Known cells map `light` to 8 bands, from cold navy at the lit edge to warm amber where the knight walked (`bandOf` in app.js). `bandOf` assumes `light` runs 0.2 to 1 and clamps lower values; see [open issues](#open-questions--known-issues).
  - Unknown cells get a flat navy-to-black glow by distance (1-5) to the nearest known cell. `computeFog` runs an 8-way BFS over **`light` only** and is recomputed per view, not per frame.
  - **Never draw unknown walls or read `tiles` for unknown cells unless Reveal is on.** `wallShown` treats an unknown cell in front as not hiding a face, so no gaps leak the layout.
- Reveal map (debug) draws unknown floors, walls, the chest and ghosts at `REVEAL_ALPHA = .42`.
- Easing: newly lit cells fade in through `shown[][]` over `FADE_MS = 300` ms.
- Sprites (`public/sprites.js`):
  - `buildSprites()` returns `{ knight, ghost, chest }`, each `{ canvas, w, h, anchorX, anchorY, frames? }`.
  - Art faces right, at 1 canvas px per art px. The anchor is the point on the cell centre: the feet, or the hover point under the ghost.
  - Knight 18×24 with anchor (9,23); ghost 18×20 with anchor (9,19); chest 12×10 with anchor (6,9).
  - `export const ART` holds the raw grids.
  - `app.js` imports the module dynamically with stand-in fallbacks, so a broken `sprites.js` only shows placeholder shapes and a console warning.
- **Facing rule:**
  - Facing is the sign of the change in `x - y` (screen x).
  - Moving `right` or `up` faces right; `left` or `down` faces left.
  - With no movement, the character keeps its last facing.
  - Facing is tracked per adversary id, plus `'@'` for the explorer, and resets only on Reload (`syncActors(true)`).
  - Mirroring is `scale(-1,1)` around `anchorX`.
- Entities tween over 150 ms with smoothstep. A ghost that jumped more than one cell, or wasn't drawn last time, snaps instead of streaking.
- **Slash animation:** every strike (either side) also draws a pixel crescent (`drawSlash` in app.js, `SLASH_MS` 340, six frames, drawn per pixel so the art stays crisp) in the 'edge' pass, after the entities. It sweeps around the attacker's cell (`strike.from`, recorded by `resolveAttack` because the explorer has often stepped on before the view arrives) through the centroid of the struck cells: white-blue for the explorer's sword, red-white for a ghost's claw, dimmer on a `miss`. Fog rule as for the diamonds: only cells that are lit (or Reveal) draw a slash. Visual only.
- Skills and bumps: the UI draws `view().strikes` as red/steel diamonds (hidden unless Reveal, like ghosts), a shield glyph while `view().block` is set, ghost hp pips (Reveal) and a Skills block in the pane; log lines come from `struck`, `dispelled`, `strike`, `blocked` and `bump` events.
- Damage: a `hit` event logs "a1 hit Jev — 1 life left" (red, `li.hit`) and flashes the board red (`.board-wrap.hit::after`, 450 ms). While `game.invulnerable` the knight blinks (`BLINK_MS = 120`). The final loss shows the overlay title "Jev lost all lives".
- Ghosts bob 2 px over 1.6 s and cast a floor shadow. A chasing ghost has a red pulsing glow, and a ghost with its brain on shows a cyan marker.
- The minimap stays top-down, is rebuilt only when `miniDirty` is set, and draws the rotated viewport outline.
- Theme:
  - Dark only: navy/stone with an amber accent, square corners, hard shadows, monospace font.
  - Two columns (board + 340 px pane). Below 860 px the board is 70dvh and the page scrolls.

## Open questions & known issues

- **Portal motivation:** fixed in the explorer rules, moods, encounter facts and legacy leave question. First portal sighting commits the resumed plan to `go_to_exit`; five live comparisons should guide further memory and combat changes.
- **Linear maps: guardians drift.** With `adversaryCharacters` off every ghost is `standard` and patrols the whole map, so the portal-room ghost and side-room guardians wander off their rooms within a few dozen ticks. Holding them near their spawn would need a patrol radius in `adversary.js` (adversary agent's file); not done.

- **Chase trigger.** The user wrote "line of sight … and at least 7 steps away"; the code builds "within 7" pending confirmation. The flip is one operator in `startsChase` (adversary.js:156). Because `seesExplorer` already caps distance at `SIGHT_RANGE = 7`, an "at least 7" trigger also needs a larger `SIGHT_RANGE`.
- **Reveal toggle doesn't resync actors.** It only sets `miniDirty` (the Reveal checkbox `onchange` in app.js). A ghost revealed mid-game can tween (streak) across the fog on the next step instead of snapping.
- **Mid-tween occlusion.** If a new view arrives mid-tween, the walking knight can briefly draw over a wall in front of it.
- **Trail dots** are hard to see on the amber floor. Reveal-mode unknown walls look slightly too bright.
- **Encounter tactics (v4).** `escape` was renamed `run_away` (CONTRACT.md says `run_away` now). `run_away` never fails by gap, so a chaser that stays in sight triggers no re-decision. `carry_on` is effectively unreachable while `CHASE_RANGE == SIGHT_RANGE` (the defaults; the settings page can separate them).
- **`run_away` in a closed room.** With a close ghost in a room with no way out, `run_away` can still shuttle from corner to corner. The answer there is `slip_past` or `engage`, which `run_away` doesn't decide. Tabu T3 now rules a shuttling `run_away` out after 12 ticks with no gain (`check-tabu` 4k, `check-dungeon` 4f), and the move level only dampens it (minMoves 2 keeps the way back). In the 2026-10-13 live runs (PLAN-tabu, Live comparison) the real Jev engaged and never shuttled.
- **`check-dungeon --measure` is stale.** It still samples sizes 140..150 and labels them "~150x150" (check-dungeon.mjs:919). With the default `MAX_SIZE = 90` no seed qualifies, so the large-map timing is empty or may break. The minimum-size sample (section 6, check-dungeon.mjs:971) uses 35×35, not 25×25. Not yet run.
- **Renderer light floor.** `bandOf` assumes `light` runs 0.2 to 1. With `LIGHT_RADIUS = 7` it goes down to 0.13 and everything below 0.2 lands in the coldest band, so the outer ring of each light pool looks flat.
- **Walker stats.** Even the `flee` policy in `check-adversaries.mjs` is often caught or times out. The stats are informational, not asserted, and useful for tuning speed and ranges.
- **Request size.** The largest explorer decision tick is about 9-10 KB (asserted ≤ 9500 bytes for a chasing adversary with 5 tactics, ≤ 10500 for a patrolling one with 6, in `check-dungeon.mjs`). The ghosts' requests are smaller. A new state field or longer option text can break these bounds; if you raise them on purpose, say why here.

Motivation P3 (the odds in the combat rule, the fight numbers in engage's fact) added about 300 B to the `check-dungeon.mjs` busiest ticks (7321 / 7906 B to 7620 / 8205 B). The P2/P3 review added a true worst case to `check-dungeon.mjs` (all 5 / 6 tactics incl. `slip_past` and `race_to_exit`, three lit coin piles within 8 steps, a remembered second ghost, two hits): it measured 9552 / 10138 B (9871 / 10457 B with a full `plan.tried`), over the chasing bound, so the review cut text instead of raising it: the "Away from N seen coins" move fact, the repeated "then strike first" in engage's target facts, "Never step onto it." in engage's move hint, "or wins a fight worth its risk (engage)" in the tactic priorities (the next line covers it), and `plan.tried` on the tactic request (no review rides on it). Now about 9.25 / 9.83 KB at worst with a full `plan.tried` (the check's own run: 9038 / 9602 B after P6, 8978 / 9542 B after P7a, which dropped the mood and generic lines from the engage move questions), about 250 / 670 B left. Not built: the `mood` layer, a `wait` skill; the `caution` trait is reserved (it only wakes `keepDistance`).

## Monster morale (PLAN-monster-morale)

The ghost-side twin of the explorer's confidence, built from PLAN-monster-morale.md (M0-M7). Behind the **`monsterMorale`** toggle (Adversaries group, `monsters.morale.enabled`, default **off**, `when: 'next'`; independent of `adversaryCharacters`). With it off there is no morale state and monster requests are byte-identical to today's.

- **The score.** `M = combine(capability(...), history)`, 0..100, in `src/characters/adversary/morale.js` (pure, imports nothing, on the section 0b allowlist, so no guard changes and the explorer's `confidence.js` is untouched). It is called *morale*, not confidence, because `confidence` already means Jev's own answer confidence here (`memory.latest_action.confidence`).
  - **Capability R** (fog-safe, all of it already readable): own hp, how many sword strikes would finish it (`ceil(hp / swordDamage)`, passed in by adversary.js because the guard forbids importing `skills/*`), `view.explorerArmed()`, whether it is stunned, and packmates hunting within its alert reach weighted by its `pack` trait.
  - **History H** (events, each queued where it happens and applied in one phase): `clawed` +8, `wounded` -10 scaled by the share of health lost, `blocked` -5, `shrugged` -2 (a claw that landed during grace), `packmate_lost` -15 (the death cry), `help_came` +4 (ceiling 65), `cornered` +3 (ceiling 65), `slipped` -2 (at most -8 per hunt), `gave_up` -6, and `regen` toward the character's baseline after 10 quiet ticks. Every negative is scaled by the character's sensitivity.
  - **The hp cap** is applied by `combine` only (not by `apply`): 100 at full hp, 40 on the last hit point, else `100 * (0.3 + 0.7 * hp/maxHp)`. So a wounded monster can never be in the high tier, and a character's baseline is never counted against it twice.
- **Character.** Four new rows in `character.js` `TABLE` (so central-config P2's trait tables tune them): `moraleStart` (aggression 40/55/70), `moraleRegen` (persistence 0.15/0.25/0.40), `moraleHurt` (**caution** 0.6/1.0/1.6 — the first real use of the reserved trait; every preset stays at level 2, so nothing changes outside the toggle), `moralePack` (pack 0/0.5/1). An `aggressive` monster opens the high tier; a `timid` one routs from one wound where a `standard` one only turns skittish.
- **Moods** (`MOODS`, two per tier plus `rout`): low `skittish`, `cagey`; mid `stalking`, `pressing`; high `relentless`, `frenzied`. `stalking` is the **identity row**: a mid-tier monster behaves exactly as it does with morale off. Each row moves `keepDistance` (waking the previously dormant hook in `adversary/brain.js`), the strike line level (1-3 of `STRIKE_LINE`), `keepHuntingMin`, `maxSearchTicks`, whether it calls for help even as a loner, and which search approach it leans to; `knobsOf()` in adversary.js overlays them on the character's own numbers. `moodFor` picks the bolder of the tier's two moods in the upper half of the band, with hysteresis at both the tier and the mood edge.
- **Rout.** Code enters it below M **12** and leaves it at **20** — deliberately lower than the explorer's panic (20/25), because a monster has less survival instinct (owner's decision). The monster **breaks off**: `turnOff` with reason `routed: ...`, so `mode` goes back to `patrol` and no new `mode` value exists (the explorer must never read a fleeing monster as `chase`, which its own `pressed` confidence event and `threats.visible[].chasing` key off). It will not start a new hunt for `ROUT_REST` = 8 ticks and emits `{ id, type: 'routed', at, morale }`.
- **Order and determinism.** One morale phase per tick inside `stepAdversaries`, after the bump checks and sensing and **before** budgets and the parallel Jev calls, walked in id order. Events that happen during the explorer's turn (`wounded` from `takeHit`, the death cry from `game.dispelled`) land the same tick; a monster's own claw result lands the next one. No `rng()` call is added anywhere, so rule 8 holds.
- **What Jev reads** (zero extra calls: it all rides on the request the hunting monster already sends): `self.morale` as `"48 steady"` (bands savage / eager / steady / wavering / broken), the mood's priority line (<= 110 chars, empty for `stalking`), one `keep_hunting` clause, and one sentence in `rules()` that finally makes the objective honest — the explorer's sword can dispel it and dispelling it removes a pursuer on the explorer's way to the portal, so surviving is part of its objective. Monster morale **never** reaches an explorer request, and the raw state never leaves the server (only the banded word).
- **Cost.** Measured over 6 generated dungeons x 120 ticks: calls per tick unchanged (0.10 -> 0.11, within the merge noise of one extra hunt), request bytes avg 5405 / max 7282 with morale on against 5173 / 6932 off, inside the `REQUEST_BYTES` bounds 5500 / 8000. The wording was cut once already to buy that headroom: shorten something before adding more.
- **UI.** `view().adversaries[].morale` is `{ value, tier, mood }` (Reveal-only display, like `character`), and an unknown `routed` event already logs as `a1: routed`. Drawing it on the board is still open (see [open issues](#open-questions--known-issues)).
- **Checks:** `check-morale.mjs`, `check-morale-wiring.mjs`, `measure-morale.mjs`, plus `measure-memory --who adversary --morale on` for the size bounds.

## Confidence, tiers and moods (PLAN-moods; builds on PLAN-confidence-mood)

Confidence caps are the only model (the `confidenceModel`, `confidenceMeter` and `confidenceCaps` settings and the old four-mood table are gone). C = `combine(capability(...), history)` from own lives, the live skill numbers and the brain's `#seen` sightings (fog-safe).

- **History H** (`confidence.js`): events hit -7, struck +5, dispelled +8, blocked +3 (<= 65), evaded +2 (<= 65), **coin +2 per coin picked up**, **heart +5** (applied after the heal, so the lives cap sees the restored life), then the lives cap. The coin and heart events come from the explorer's own `applyMove` result (`coins`, `healed`), so they are fog-safe, restart the regen wait like any event that moves H and are named in `turn.confidence.reason`. **There is no `pressed` penalty any more**: being chased or seeing a monster is no justification for losing confidence (a drop needs harm: a hit, fewer lives, a second monster). Capability: the heaviest monster known is free (`W = clawDamage * wPerExtra * (k - heaviest)`, whatever `stunTicks` is, so a lone ghost or troll never lowers R); each further monster costs, and an **unhurt armed explorer (full lives) keeps R >= `UNHURT_FLOOR` = 50** (knob `explorer.confidence.capability.unhurtFloor`), i.e. mid tier, `bold` still offered, from sightings alone. Hurt (lives < max) there is no floor. Knobs: `confCoin`, `confHeart`, `confUnhurtFloor` (registry rows; `confPressed`, `confPressedMax`, `confPressedRange` are gone); memory `progress.confidence.counts` is `{ strikes, blocked, evaded, coins, hearts }`. **Regen**: every tick the brain emits `regen`, which moves H 0.25 toward 50 from either side, but only once `REGEN_WAIT` = 10 ticks have passed since H last changed (`state.idle`; another event that moves H restarts the wait, regen does not).
- **Tiers** (`tierOf(C, prev)`): low <= 35, **midlow** 36..49, mid 50..69 (`TIER_MID_MIN`, knob `explorer.confidence.tiers.midMin`), high >= 70, held 5 points past an edge by the current mood's tier (`tierOfMood`: a mood in several tiers belongs to the first of low, mid, midlow, high, so `steady` and `bold` are held in mid down to 45 and `cautious` in midlow up to 54). **Moods** (`SENTIMENTS` in brain.js, ids in `MOOD_IDS` in memory.js): low `wary`, `guarded` (+ `panic`), midlow `cautious`, `steady`, `bold`, mid `steady`, `greedy`, `bold`, high `bold`, `fearless`. `allowedMoods(C, { lastLife, swordDown, current })` lists the tier's moods; a last life or a chaser close by with the sword down force the low tier.
- **The mid ground (why midlow exists).** Jev takes whatever safe option it is shown, so in the middle it used to pick `cautious` and then `run_away` / `hide` almost every time. Now the safe options are kept for when confidence is really lower: `cautious` (reworded as a retreat *for a while*: pull back, regroup, come back for the loot) is only offered in midlow, and the retreat tactics `run_away` and `hide` are left off the tactic menu (`tacticFeasibility(..., { retreat: false })`) while a forward tactic (`engage`, `slip_past`, `carry_on`) is open. The brain's `#retreatOK` allows them in panic, under a low or midlow mood (`wary`, `guarded`, `cautious`), with C in the low or midlow tier (a last life or the sword down with a chaser close count as low), with more than 3 enemies in sight (more than the engage hold covers), under a live player directive, or with the `fixedMood` arm (checks). With no forward tactic open, or while cornered (`cornered`, cornerMode), the menu is not trimmed. The sentiment question's "Tactics it leaves here" list follows the same gate per mood. `steady`'s `when` no longer offers itself as a way to dodge a fight. An unhurt explorer has R >= 50 (`UNHURT_FLOOR`), so with neutral history it never drops below mid: midlow is reached after a hit (with 3+ lives) or a history that went badly. With 4 default lives, a hit can reach midlow before the last-life low-tier gate; the old 2-life setup usually jumped from mid to low. Live gyms (real Jev, 13x9 arena, 2 ghosts in sight, 2026-10-08): 10 mid-tier games (C 58-60): no retreat offered, engage on every chasing encounter, 8 won (cleared), 2 unfinished at 12-14 ticks, 0 hits; 3 midlow games (C 43-46, forced through `confCapabilityMax` 60 / `confUnhurtFloor` 40): `cautious` 27-66% of the mood picks and `run_away` 14-99% of the tactic picks, 0 hits. The start C (70) is high, so Jev begins confident (bold or fearless) and takes on enemies unless something lowers it. **Objective**: win by reaching and stepping through the portal; score = coins held. Dispelling enemies permanently removes obstacles and pursuers. On first sighting, the brain commits to `go_to_exit`, replacing an interrupted exploration plan while preserving player directives. Legacy `leave_now` remains a fallback, not a gate to winning. In the low tier, panic or `cautious` (midlow's retreat), hurt, with a lit heart reachable by a route 2 steps clear of every enemy, `run_away` targets the heart (`heartRun` in `tacticFeasibility`, set by the brain's `#heartRun`). A tier change swaps the mood silently out of sight (`defaultMood`: steady, else guarded, else bold), or fires the once-per-direction `confidence` trigger in sight.
- **panic**: code enters it below C 20 and leaves it at C >= 25 (`panicNext`), with no sentiment call (`#askSentiment` returns it). Its tactic menu is `run_away`, `race_to_exit` and, only when `blocksOnlyRoute` (encounter.js, known floor and visible enemies only) says the enemies shut the only known way out, `engage`. The engage hold and the fight lines are off, its text never mentions lives, and a whisper-bar directive is not applied (and not sent) while it lasts; it still runs out.
- **Wording**: everything Jev reads from the explorer side says enemy / monster, with no counts or numbers about enemies (no strike, hp or claw gates). `#fightOn` only decides whether the stakes sentence and the default engage line are sent: sword ready, not panic, not low tier, and a single or hurt monster, or the high tier. The ghosts' own requests are unchanged.
- **UI**: `MOOD_THOUGHTS` (app.js) has >= 3 lines per mood; the explorer's bubble draws one at random when the approach changes (a mood change alone does not re-show it). `check-moods-ui.mjs` checks pools, notes and tints.
- Checks: `check-confidence.mjs` (section 13 regen/tiers/panic, 12(d) allowedMoods), `check-confidence-wiring.mjs`, `check-confidence-caps.mjs` (section 8 panic), `check-moods-ui.mjs`, `check-request-hashes.mjs` (one fixture, `request-hashes.json`). `measure-caps.mjs`, `measure-confidence.mjs` and `calibrate-confidence.mjs` still carry the old arms (`off`, `true`, `'caps'`) and are stale: only their caps arm means anything now.

## Tabu (PLAN-tabu)

Hard exclusion of options that kept failing: the option is taken **out of the request**, so Jev must pick another one. Built: phases 0-5 (the module, the explorer's tactic level, its moods and its moves, the monsters' moves and search approach) and 6 (`scripts/measure-tabu.mjs`; free and live results in PLAN-tabu.md: with a stalling stub tabu cuts the longest repeated-cell run from 10.2 to 6.0 and deaths from 50 to 34 of 65 games, with a fighting stub nothing changes, and in 16 live games it never fired because the real Jev did not stall). **On by default** (`explorer.tabu.enabled`, `.tactics`, `.moods`, `.moves`; file-only, `live`); off is byte-identical to the code before tabu.

- **Module** `src/characters/shared/tabu.js`: pure, imports nothing, no clock, no rng (on both fog-guard allowlists in `check-dungeon.mjs`). Entries `{ level, attr, since, until, encounter, reason }`, strike counters, `filterOptions(ids, tabu, level, step, { keep, min })` with aspiration (never removes `keep`, never below `min`; lifts the least tenure left first). The brain's tabu state is private (`#tabu`), never in `memory.json`, never sent to Jev.
- **Rules (tactic level)**, all judged on a *gain* baseline (a strike or dispel landed, a life came back, the nearest enemy `TABU_GAP_GAIN` = 2 steps further off, or C up 5; a gain moves the baseline to now): **T1** a ping-pong `tactic_failed` with no gain during it (`explorer.tabu.pingpongTenure` 8 steps); **T2** `tacticStrikes` (2) re-decisions (`tactic_failed`, `hit`, `confidence`) under the same tactic with no gain since the last decision (rest of the encounter); **T3** `run_away` / `hide` on for `retreatTicks` (12) with no gain (rest of the encounter); **T4** `engageHits` (2) hits under `engage` with no strike landed (rest of the encounter). A ruled-out current tactic fires `tactic_failed` (within `REDECIDE_COOLDOWN`). An encounter's start and end clear the encounter entries and every strike.
- **Filter** (`#menu`): the tactic menu and the moods' "Tactics it leaves here" lists. Aspiration: `race_to_exit` never removed, a last life never rules out a retreat, the menu never empties; stands aside in panic and under a live directive. One tactic left = code takes it, no Choice (as before).
- **Rules (mood level, phase 2)**, same gain baseline, tracked per mood pick (`#moodTrack`): **D1** `moodStrikes` (2) sentiment re-decisions (`tactic_failed`, `hit`, `confidence`) with the mood picked last still on and no gain since the last decision rule it out until the encounter ends and for at least `moodTenure` (10) steps (`#endTabuEncounter` turns the entry into a timed one); **D2** `moodStrikes` approach reviews in a row that judged the approach failing (`approach_working` under 0.5) under the same mood rule it out for `moodReviewTenure` (20) steps outside any encounter; a review that judged it working resets the count. Filter (`#moodMenu`) right after `#allowed(caps)` in `#askSentiment` (criteria and the question's mood list; one mood left = code takes it) and in the tier-swap block of `takeTurn` (the current mood ruled out: silent swap to `defaultMood`, or with an enemy in sight a `confidence` re-decision latched once per encounter under the key `tabu`). Aspiration: panic is never tabu, the `fixedMood` arm and a live directive are exempt, a tier is never emptied (the never-empty rule lifts the entry with the least tenure left, so a last life or a close chaser with the sword down never loses both `wary` and `guarded`). Memory event `Ruled out cautious: picked 2 times with nothing gained.` (D2: `2 approach reviews in a row judged the approach failing.`). Knobs `explorer.tabu.moodStrikes`, `.moodTenure`, `.moodReviewTenure`.
- **Rules (move level, phase 3)**: moves are ruled out by destination **cell** (level `cell`, attr `x,y`) or `stay` (level `move`), never by direction word; each tick the cells are turned back into the directions that lead there. Scored at the start of the tick (`#scoreMoves`, after aging): **M1** the last move returned to the cell two back and `recent.back_and_forth` >= 2 -> the cell stepped back to is out for `bounceTenure` (6) steps; **M2** a cell entered `loopVisits` (3) times in the last `loopWindow` (12) steps (the brain's private `#cellRing`, since `memory.recent.cells` holds 8) -> out for `loopTenure` (8); **M3** `stay` chosen `stayRun` (3) ticks in a row, hold ticks excepted (they break the run) -> `stay` out for `stayTenure` (4). M1 and M2 stand aside for 12 steps after a strike or dispel landed (`#winStep`): close in, strike, step back is a fight, not a stall. One filter per tick (`#moveMenu`, after the hold and the tactic menu are known) feeds `#moveQuestion` (`next_move`, every `move_if_<tactic>`, `surroundings.moves`) and the answer validation (`moves.includes(choice) ? choice : moves[0]`). Aspiration: **A1** the portal step is never removed; **A2** when no safe move would remain (`describeMoveParts` now returns `safe` per move, no text change: not onto an enemy, not below the gap) the safe removed ones come back; **A3** under (or deciding) `engage` the steps toward the engage target (its own cell = `stay`) stay, and under `hide` `stay` on the hiding spot; **A4** cornered (`#cornerOpt()`): cells are not ruled out, only `stay`; **A5** `minMoves` (2): never fewer moves by tabu alone. Not on a hold tick, not under a live directive; panic is not exempt (it only runs, A2 keeps the safe way out). One move left after the filter (only with `minMoves` 1): code takes it, no move question, `turn.tabu.forced` (`turn.forced` stays `moveDecision === null`). `#lethalWalkIn` still runs after the answer and may turn the move into `stay` even if `stay` was removed. Memory event the first time a request really drops a move: `Ruled out the cell to the west for 6 steps: kept stepping back and forth.` / `... kept coming back to it.` / `Ruled out standing still for 4 steps: stood still 3 times in a row.` Knobs `explorer.tabu.moves`, `.bounceTenure`, `.loopWindow`, `.loopVisits`, `.loopTenure`, `.stayRun`, `.stayTenure`, `.minMoves`. `#bounce()` / `#exclude` (tactic targets after a tactic ping-pong) are untouched until phase 4.
